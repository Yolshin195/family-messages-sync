# ТЗ: минимальные доработки для пробного запуска

Цель — запустить `family-messages-sync` на Mac владельца в фоне и пару недель проверить на настоящих SMS KBank.
Большое ТЗ (`docs/tz.md`) не ждём: берём из него только то, без чего пробовать нельзя.

Два требования:

1. **Одна покупка — одна операция.** SMS не создаёт операцию, если она уже внесена (вручную или раньше этим же
   SMS), а ручной ввод через Claude не создаёт вторую, если операция уже пришла из SMS.
2. **Однозначно видно, что сообщение заведено.** В бухгалтерии у операции есть служебная связь с внешней записью
   («SMS imessage:ABC-123»), которую не стирает правка. На Mac для каждого SMS видно, чем закончилось.

## 1. Что есть сейчас и почему этого мало

Приложение помечает свои операции текстом `[sms:guid]` в заметке позиции и по нему узнаёт, что SMS уже
отправлялось. Ручные операции, «занятые» каким-то SMS, помнит только локально в `state.json`.

| # | Проблема | Доработка |
| --- | --- | --- |
| 1 | Метка — свободный текст: правка операции в форме на сайте стирает заметки позиций (`transactions/src/adapters/web.rs`: `note: None`), и связь с SMS пропадает | Б1, Б4 |
| 2 | У ручной операции, к которой «прикрепилось» SMS, в бухгалтерии нет никакого следа; после сброса состояния или со второго Mac её «займёт» другое SMS | Б1, П5 |
| 3 | Удалённая операция из SMS создастся заново при повторной обработке того же SMS | Б1 |
| 4 | SMS пришло раньше, чем покупку внесли через Claude → две операции | Б3 |
| 5 | Что стало с сообщением, видно только в `out.log`; ошибки в фоне никто не замечает; подкачка истории iCloud заводит старые SMS | П1–П4 |

## 2. Бухгалтерия (family-budget) — один PR

### Б1. Связи операций с внешними записями

Новая таблица в фиче `transactions`. Связь — служебные данные: форма, `PUT` и `update_transaction` её не видят и не
меняют.

**`fb_external_refs`**

| Колонка | Тип | Что |
| --- | --- | --- |
| `id` | `UUID` PK | |
| `project_id` | `UUID NOT NULL` | |
| `provider` | `TEXT NOT NULL` | Кто прислал: латиница, цифры, `_`, до 40 знаков, нижний регистр. Сейчас — `imessage`; дальше `telegram`, `bank_statement`, `apple_pay` |
| `external_id` | `TEXT NOT NULL` | Id записи у провайдера, до 200 знаков. Для SMS — guid сообщения из `chat.db` |
| `transaction_id` | `UUID NOT NULL` | Операция. **Без внешнего ключа:** операция может быть удалена, а связь остаётся, чтобы то же SMS не завело её снова; «Отменить» удаление возвращает операцию с тем же `id`, и связь снова работает |
| `link` | `TEXT NOT NULL` | `CREATED` — внешняя запись создала операцию; `MATCHED` — прикреплена к уже внесённой |
| `received_at` | `TIMESTAMPTZ NULL` | Когда внешняя система получила запись (время SMS) |
| `created_at` | `TIMESTAMPTZ NOT NULL` | Когда прикреплено |
| `created_by` | `UUID NOT NULL` | Пользователь (владелец токена) |

- Уникальный ключ `(project_id, provider, external_id)`: одна внешняя запись — не больше одной операции.
- Индекс `(project_id, transaction_id)`.
- У одной операции может быть несколько связей: SMS, позже строка выписки того же платежа.
- Удаление проекта стирает связи (`purge`). Удаление операции связи не трогает.
- Счёт в ключ не входит: guid SMS уникален сам по себе, а соответствие «карта → счёт» может поменяться.
- Адаптеры PostgreSQL и памяти, миграция с `down`.

**REST**

| Запрос | Что делает |
| --- | --- |
| `POST /api/transactions` | Новое необязательное поле `external_ref: {provider, external_id, received_at?}`. Связи с такой парой нет → операция создаётся вместе со связью `CREATED` в одной транзакции БД, ответ `201`. Связь есть и операция существует → ничего не создаётся, ответ **`200`** и существующая операция. Связь есть, а операция удалена → **`409`**, код `external_ref_deleted` и `transaction_id` |
| `POST /api/transactions/{id}/external-refs` | Прикрепить внешнюю запись к существующей операции: `{provider, external_id, received_at?}` → связь `MATCHED`, `201`. Эта же пара уже у этой операции → `200`. Пара у другой операции → `409`, код `external_ref_exists` и её `transaction_id`. Операция не найдена → `404`. Начальный остаток → `422` |
| `GET /api/transactions`, `GET /api/transactions/{id}` | В каждой операции — `external_refs: [{provider, external_id, link, received_at}]` (пусто — нет связей). Новый фильтр `external_provider` — только операции со связью этого провайдера |

- Права — как у остальной `/api/transactions`: создание и прикрепление требуют `transactions:write`.
- Ошибки — через `error::Problem`, тексты в `i18n.rs` на трёх языках.
- Гонка двух одинаковых `POST` решается уникальным ключом: второй получает `200` с операцией первого.
- Отвязать связь в этом PR нельзя (см. «Вне рамок»).

**Сайт**

- В ленте операций у операции со связью `imessage` — значок «SMS» (ru/en/th: «SMS»), подсказка при наведении:
  «Из SMS банка · 21.09 10:51» или «Подтверждено SMS банка · 21.09 10:51» для `MATCHED`.
- В форме правки — та же строка только для чтения под заголовком.

**MCP**

- `list_transactions` и ответ `update_transaction`: у операции поле `sms` — `{received_at, link}`, если есть связь
  `imessage`. Новый необязательный фильтр `from_sms: true`.
- Через MCP связи не создаются.

### Б2. Форма не стирает заметки позиций

Ошибка, которую нашли попутно; без Б1 она ломала бы связь с SMS, с Б1 — просто теряет текст.

- В режиме формы (`replace_items = true`) позиция с тем же `id` сохраняет прежнюю `note`, если форма её не
  прислала. Новая позиция — без заметки.
- `update_transaction` в MCP и `PUT` с правкой по `id` уже сохраняют заметку — не менять.

### Б3. Claude дополняет операцию из SMS, а не создаёт вторую

Абзац в `INSTRUCTIONS` (`crates/features/mcp/src/adapters/server.rs`), по-английски, как вся инструкция:

> Some transactions were created from bank SMS (they have `sms` with `link: CREATED`): their amount, account and
> date are facts, category and description are placeholders. Before add_expense or add_income for a purchase that
> may already have reached the bank, call list_transactions with from_sms: true for that account and the purchase
> date ±1 day. If one has the same amount and direction and still has its placeholder category, update it with
> update_transaction (category, place, for, description, translations, items) instead of adding a new one, and
> tell the user "updated the transaction from the bank SMS of <date> <time>". Add a separate transaction only if
> the user says it is a different purchase.

### Б4. Тесты, документация, «Что нового»

- Тесты сервиса (память и PostgreSQL, как остальные use cases `transactions`):
  - создание с `external_ref` → `201` и связь; повтор → `200`, та же операция, операций по-прежнему одна;
  - повтор после удаления → `409 external_ref_deleted`; после «Отменить» — снова `200`;
  - прикрепление: `201`, повтор `200`, к другой операции `409 external_ref_exists`;
  - правка формой и `PUT` не меняют связи;
  - фильтр `external_provider`; изоляция проектов; `purge`.
- Тест Б2 в `domain.rs`: заметка переживает правку формой.
- Тесты `templates_are_translated` проходят с новыми строками.
- `docs/group-1.md` (шаг 4, раздел 4.1 и 5.5), `docs/platforms.md` (этап C): колонку `external_ref` в операции
  заменяет таблица `fb_external_refs` — записать решение и ключ `(project_id, provider, external_id)`.
- «Что нового» — `site/content/releases/next/` (по три файла):
  - `bank-sms-badge` (`change = "new"`): «Операции, которые пришли из SMS банка или подтверждены им, отмечены
    значком SMS»;
  - `item-notes-kept` (`change = "fixed"`): «Правка операции на сайте больше не стирает заметки к позициям,
    добавленные через Claude или API».

## 3. Приложение (family-messages-sync)

### П1. Журнал сообщений `app.db`

SQLite в каталоге конфига (`~/.config/family-messages-sync/app.db`), `rusqlite` уже подключён. Таблица — подмножество
`messages` из `docs/tz.md` 11.1, чтобы её без переделки взяло десктопное приложение.

| Поле | Что |
| --- | --- |
| `rowid` PK | ROWID из `chat.db` |
| `guid` | guid сообщения |
| `sender` | `handle.id` |
| `received_at` | время получения, RFC 3339 |
| `text` | текст SMS; у сообщений из `ignore_patterns` (OTP) — пусто |
| `status` | `CREATED`, `MATCHED`, `ALREADY_SENT`, `DELETED`, `REJECTED`, `UNRECOGNIZED`, `IGNORED`, `OLD` |
| `reason` | текст отказа, ошибки или пропуска |
| `kind`, `amount`, `account_code`, `occurred_on` | разобранные поля (пусто, если не разобрано) |
| `transaction_id` | созданная, найденная ручная или прежняя операция |
| `processed_at` | время последней обработки |

- Запись — `INSERT … ON CONFLICT(rowid) DO UPDATE` после каждого сообщения, вместе с сохранением `state.json`.
  Сообщения не от банка не пишутся; «свежее, ждёт» — тоже (ещё не обработано).
- `--dry-run` в журнал не пишет. Срок хранения — 90 дней по `received_at`.

Команда **`log [N] [--status S]`** — последние N записей (по умолчанию 20):

```
#48211  21.09 10:51  расход 60.00 CARD_KBANK 21.09   создано         https://…/transactions/<id>/edit
#48215  21.09 12:40  расход 89.00 CARD_KBANK 21.09   найдена ручная  https://…/transactions/<id>/edit
#48220  21.09 13:02  —                               не распознано   «Your statement is ready…»
```

`show` дополнительно показывает статус из журнала у каждого сообщения.

### П2. Уведомления macOS

Через `osascript -e 'display notification …'`, за трейтом `Notifier` (в тестах — запись в вектор). Ошибка запуска
`osascript` не мешает обработке.

| Когда | Текст | Как часто |
| --- | --- | --- |
| Остановка: сеть, 401, 403, 5xx, нет доступа к `chat.db` | «Импорт SMS остановлен: <причина>. Подробности: make logs» | Одна причина — не чаще раза в 6 часов |
| Сообщение попало в очередь повторов | «SMS не заведено: <причина>. См. failed.log» | Один раз на сообщение |
| Создана операция | «Из SMS: расход 60.00 THB, CARD_KBANK — проверьте категорию» | Каждый раз; настройка `notify_created`, по умолчанию `true` |
| Работа восстановилась после остановки | «Импорт SMS снова работает» | Один раз |

Уведомление о создании нужно на время проверки: увидев его, человек дополняет операцию из SMS, а не вносит вторую.

### П3. Старые сообщения не заводятся

- В `state.json` — `last_received_at`: время получения последнего обработанного сообщения от банка.
- Новое сообщение (не из очереди повторов), полученное раньше `last_received_at − 2 дня`, → статус `OLD`, не
  заводится. Подкачка истории iCloud не создаёт операции, а SMS за неделю выключенного Mac заводятся: они новее
  последнего обработанного.
- `run --from-rowid N` отсечку не применяет.
- Больше 20 `OLD` за запуск — одно уведомление «Пропущено N старых SMS — похоже на подкачку истории».

### П4. Команда `status`

```
Последний запуск:  24.10 14:05 (ок)
Последняя ошибка:  23.10 09:10 — 401 токен недействителен (исправлено)
Последнее SMS:     #48220, 21.09 13:02
Очередь повторов:  0 · Не распознано за 7 дней: 1 · Создано за 7 дней: 12 · Найдено ручных: 30
```

`last_run_at`, `last_ok_at`, `last_error` — в `state.json`, счётчики — из `app.db`. `make status` вызывает и её.

### П5. Переход на связи бухгалтерии

Метка в заметке и локальный список «занятых» операций заменяются связями Б1.

Обработка сообщения (`external_ref = {provider: "imessage", external_id: guid, received_at}`):

1. Запросить операции по счёту за дату SMS ±`date_tolerance_days`.
2. Есть операция со связью `imessage` на этот guid → `ALREADY_SENT`, конец.
3. Кандидаты на ручную пару — как сейчас (счёт, направление, сумма, дата, переводы, возвраты), но **без связи
   `imessage`** (она уже подтверждена другим SMS). Ближайший по дате → `POST /api/transactions/{id}/external-refs`:
   - `201`/`200` → `MATCHED`;
   - `409 external_ref_exists` → `ALREADY_SENT` с операцией из ответа;
   - `409` у операции (её только что занял другой SMS) → взять следующего кандидата, иначе создавать.
4. Пары нет → `POST /api/transactions` с `external_ref`:
   - `201` → `CREATED`; `200` → `ALREADY_SENT` (операцию создал прошлый запуск, ответ не дошёл);
   - `409 external_ref_deleted` → `DELETED`: операцию удалили намеренно, не создаётся, уведомления нет.
5. Ошибки сети и сервера — как сейчас (`Stop`), отказы — как сейчас (очередь повторов).

Что убрать и оставить:

- Убрать `claimed` из `state.json` и метку `[sms:guid]` из заметки. Текст SMS в заметке позиции оставить (при
  разборе видно, что это было), без метки.
- Метку `[sms:…]` в старых заметках читать как раньше, чтобы операции, созданные до перехода, не задублировались.
- Категории `AUTO_*` и пометка `[АВТО: проверить]` в описании остаются: это отметка «проверить» до флага
  `needs_review`.
- `init` проверяет, что бухгалтерия знает `external_ref`: запрос `GET /api/transactions?size=1` возвращает поле
  `external_refs`; нет — «Обновите Семейную бухгалтерию: нужна версия с поддержкой связей SMS».

### Тесты приложения

- `dedupe`: операция со связью на этот guid → уже отправлено; ручная со связью другого SMS — не кандидат; старая
  метка `[sms:…]` по-прежнему узнаётся.
- Разбор ответов `POST` (`201`, `200`, `409 external_ref_deleted`) и прикрепления (`201`, `200`,
  `409 external_ref_exists`).
- Журнал: каждый статус, `REJECTED` → итоговый статус, `--dry-run` не пишет, чистка 90 дней (SQLite в памяти).
- Отсечка: старое → `OLD`; очередь повторов и `--from-rowid` не отсекаются.
- Уведомления: одна причина дважды за 6 часов → одно; восстановление → одно.
- `cargo test`, `cargo clippy` — без ошибок.

README: связи вместо метки, команды `log` и `status`, `notify_created`, «Как проверить, что сообщение заведено»;
убрать ограничение «если вы внесли вручную после автоматической — будет два экземпляра» в пользу Б3.

## 4. Порядок запуска

1. Влить и задеплоить PR бухгалтерии (Б1–Б4).
2. Собрать приложение с П1–П5, `make install`, `family-messages-sync setup` (токен `transactions:write`; для `init`
   один раз нужен `write` или категории `AUTO_EXPENSE` / `AUTO_INCOME`, созданные вручную).
3. **Сухой прогон по истории:** `show 50` → ROWID SMS двухнедельной давности → `run --dry-run --from-rowid N`.
   Ожидается: почти все SMS — «найдена ручная»; строки «будет создано» — невнесённые покупки или расхождение суммы,
   счёта, даты. Разобрать каждую, при необходимости поправить `accounts` и правила.
4. Тот же `run --from-rowid N` без `--dry-run`: ручные операции за две недели получают значок «SMS»,
   невнесённые — создаются. Проверить на сайте.
5. `make fda`, `make agent`.
6. Две недели в работе: ежедневно `family-messages-sync status`, раз в неделю `log 100` и разбор операций
   `[АВТО: проверить]` (на сайте или «разберём автоматические» в Claude).

## 7. Вне рамок

Следующим шагом, по итогам проверки:

- **Флаг «не проверено»** (`needs_review`): фильтр и счётчик на сайте, снятие при правке, инструменты MCP
  `list_review`, `mark_reviewed` (`docs/tz.md` 10.3–10.4). Заменит категории `AUTO_*` и пометку в описании.
- **Отвязать SMS** от ошибочно сопоставленной операции (кнопка на сайте) и «Это другая покупка».
- Сопоставление с ручными операциями на сервере вместо приложения, отдельное право `autoimport:write`,
  пакетная отправка.
- Дополнение операции из SMS при ручном вводе на сайте (быстрый ввод); сейчас — только через Claude (Б3).
- `client_id` для повторной отправки с устройств — можно хранить в той же таблице с отдельным `provider`.
- Цепочка остатков, сверка с остатком счёта, «Входящие», локальный веб-интерфейс, документ настроек, подпись
  бинарника, ротация логов.

Итог пробного запуска — реальные форматы SMS, доля сопоставленных с ручными, случаи дублей и ошибочных
сопоставлений. По нему уточняются следующие этапы `docs/tz.md`.
