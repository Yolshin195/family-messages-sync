# ТЗ: минимальные доработки для пробного запуска

Цель — запустить `family-messages-sync` на Mac владельца в фоне и пару недель проверить на настоящих SMS KBank,
не дожидаясь большого ТЗ (`docs/tz.md`) и шага 4 бухгалтерии (`external_ref`, `docs/group-1.md`).

Два требования:

1. **Одна покупка — одна операция.** SMS не создаёт операцию, если она уже внесена, а ручной ввод через Claude не
   создаёт вторую, если операция уже пришла из SMS.
2. **Видно, что сообщение заведено.** На Mac для каждого SMS видно, чем закончилось: создана операция (какая),
   найдена ручная, отклонено, не распознано. В бухгалтерии видно, какие операции пришли из SMS.

Остальное — `docs/tz.md` и раздел «Вне рамок» ниже.

## 1. Что уже есть и почему этого мало

Бинарник читает `chat.db`, разбирает SMS, ищет в бухгалтерии такую же операцию (счёт, направление, сумма, дата
±1 день, метка `[sms:guid]` в заметке позиции) и создаёт расход или доход с категорией `AUTO_*` и пометкой
`[АВТО: проверить]`. Мешают пробному запуску:

| # | Проблема | Где | Доработка |
| --- | --- | --- | --- |
| 1 | Правка операции в форме на сайте стирает заметки позиций, а с ними метку `[sms:guid]` и текст SMS | family-budget, `transactions/src/adapters/web.rs` (`note: None`), `domain.rs` `item()` | Б1 |
| 2 | SMS пришло раньше, чем покупку внесли через Claude → две операции | family-budget, MCP | Б2 |
| 3 | Что стало с сообщением, видно только в `out.log` | `sync.rs` | П1 |
| 4 | Ошибки в фоне (токен, Full Disk Access, отказы) никто не замечает | `sync.rs`, `main.rs` | П2 |
| 5 | Подкачка истории iCloud даёт старым SMS новые ROWID → импорт истории | `sync.rs` | П3 |
| 6 | Не видно, работает ли агент вообще | — | П4 |

## 2. Бухгалтерия (family-budget) — один PR

### Б1. Форма не стирает заметки позиций

- В режиме формы (весь чек, `replace_items = true`) позиция с тем же `id` сохраняет прежнюю `note`, если форма её
  не прислала. Остальные поля по-прежнему берутся из формы целиком.
- Новая позиция (без `id`) — без заметки, как сейчас. Удалённая позиция удаляется вместе с заметкой.
- `update_transaction` в MCP и `PUT` с правкой по `id` уже сохраняют заметку — не менять.
- Тест в `domain.rs`: позиция с заметкой → правка формой (другая категория, тот же `id`) → заметка на месте;
  новая позиция без заметки.
- «Что нового»: `site/content/releases/next/item-notes-kept.md` (+ `.en.md`, `.th.md`), `change = "fixed"`:
  «Правка операции на сайте больше не стирает заметки к позициям, которые добавил Claude или приложение».

### Б2. Claude дополняет операцию из SMS, а не создаёт вторую

Только текст инструкции MCP-сервера (`INSTRUCTIONS` в `crates/features/mcp/src/adapters/server.rs`), без новых
инструментов. Абзац (по-английски, как вся инструкция):

> Some transactions were created automatically from bank SMS: an item note contains `[sms:…]`, the description
> may start with a review marker. Their amount, account and date are facts; category and description are
> placeholders. Before add_expense or add_income for a purchase that may already have reached the bank, call
> list_transactions for that account, the purchase date ±1 day, text `[sms:`. If one has the same amount and
> direction, update it with update_transaction (category, place, for, description, translations, items) instead
> of adding a new one, keep its item notes, and tell the user "updated the transaction from the bank SMS of
> <date>". Add a separate transaction only if the user says it is a different purchase.

- Работает через уже существующие `list_transactions` (поиск по тексту в заметках) и `update_transaction`.
- Тест в `mcp/tests.rs` не нужен — меняется только текст; проверка — сценарии С3 и С4 (раздел 5).
- Отдельной записи «Что нового» не нужно: поведение касается только операций из SMS, которые пока есть только у
  владельца. В описании PR — строка о Б2.

## 3. Приложение (family-messages-sync)

### П1. Журнал сообщений `app.db`

SQLite в каталоге конфига (`~/.config/family-messages-sync/app.db`), `rusqlite` уже подключён. Таблица — подмножество
`messages` из `docs/tz.md` 11.1, чтобы её без переделки взяло десктопное приложение:

| Поле | Что |
| --- | --- |
| `rowid` PK | ROWID из `chat.db` |
| `guid` | guid сообщения |
| `sender` | `handle.id` |
| `received_at` | время получения, RFC 3339 |
| `text` | текст SMS; у сообщений из `ignore_patterns` (OTP) — пусто |
| `status` | `CREATED`, `MATCHED`, `ALREADY_SENT`, `REJECTED`, `UNRECOGNIZED`, `IGNORED`, `OLD` |
| `reason` | текст отказа, ошибки или пропуска |
| `kind`, `amount`, `account_code`, `occurred_on` | разобранные поля (пусто, если не разобрано) |
| `transaction_id` | созданная (`CREATED`), найденная ручная (`MATCHED`) или своя прежняя (`ALREADY_SENT`) операция |
| `processed_at` | время последней обработки |

- Запись — `INSERT … ON CONFLICT(rowid) DO UPDATE` после каждого сообщения, вместе с сохранением `state.json`.
  Сообщения не от банка не пишутся. «Свежее, ждёт» не пишется: сообщение ещё не обработано.
- `REJECTED` при успешном повторе из очереди меняется на итоговый статус.
- `--dry-run` в журнал не пишет.
- Срок хранения — 90 дней по `received_at`, чистка в начале `run`.
- `failed.log` и `unparsed.log` остаются как есть: журнал их не заменяет, пока нет экрана «Входящие».

Команда **`log [N] [--status S]`** — последние N записей (по умолчанию 20):

```
#48211  21.09 10:51  расход 60.00 CARD_KBANK 21.09   создано        https://…/transactions/<id>/edit
#48215  21.09 12:40  расход 89.00 CARD_KBANK 21.09   найдена ручная https://…/transactions/<id>/edit
#48220  21.09 13:02  —                               не распознано  «Your statement is ready…»
```

Ссылка — `{api_url}/transactions/{id}/edit`. Команда `show` дополнительно показывает статус из журнала у каждого
сообщения, если он там есть.

### П2. Уведомления macOS

Через `osascript -e 'display notification "<текст>" with title "Семейная бухгалтерия"'`; ошибка запуска
`osascript` не мешает обработке.

| Когда | Текст | Как часто |
| --- | --- | --- |
| Остановка (`Outcome::Stop`): сеть, 401, 403, 5xx, нет доступа к `chat.db` | «Импорт SMS остановлен: <причина коротко>. Подробности: make logs» | Одна и та же причина — не чаще раза в 6 часов |
| Новое сообщение попало в очередь повторов (`REJECTED`) | «SMS не заведено: <причина>. См. failed.log» | Один раз на сообщение |
| Создана операция (`CREATED`) | «Из SMS: расход 60.00 THB, CARD_KBANK — проверьте категорию» | Каждый раз; настройка `notify_created` (по умолчанию `true`) |
| Работа восстановилась после остановки | «Импорт SMS снова работает» | Один раз |

- Для частоты в `state.json` — `last_alert: {reason, at}` и флаг «была остановка».
- Ошибка «нет доступа к `chat.db`» происходит до цикла обработки — её тоже ловить и уведомлять.
- Уведомление о создании нужно на время проверки: увидев его, человек не вносит покупку второй раз, а дополняет
  операцию из SMS.

### П3. Старые сообщения не заводятся

- В `state.json` — `last_received_at`: время получения последнего обработанного сообщения от банка.
- Новое сообщение (не из очереди повторов), полученное раньше `last_received_at − 2 дня`, не заводится:
  статус `OLD`, причина «старое сообщение (подкачка истории?)». Так подкачка истории iCloud не создаёт операции,
  а SMS за неделю, пока Mac был выключен, заводятся: они новее последнего обработанного.
- `run --from-rowid N` отсечку не применяет: это осознанный импорт истории.
- Если за один запуск набралось больше 20 сообщений `OLD` — одно уведомление «Пропущено N старых SMS — похоже на
  подкачку истории. Если нужно их завести: family-messages-sync log --status OLD».

### П4. Состояние агента

Команда **`status`**:

```
Последний запуск:  24.10 14:05 (ок)
Последняя ошибка:  23.10 09:10 — 401 токен недействителен (исправлено)
Последнее SMS:     #48220, 21.09 13:02
Очередь повторов:  0 · Не распознано за 7 дней: 1 · Создано за 7 дней: 12 · Найдено ручных: 30
```

- В `state.json` — `last_run_at`, `last_ok_at`, `last_error: {text, at}`; пишутся в конце каждого `run`.
- Счётчики — из `app.db`.
- `make status` дополнительно вызывает `family-messages-sync status`.

### Тесты

- Журнал: запись каждого статуса, обновление `REJECTED` → `CREATED`, `--dry-run` не пишет, чистка 90 дней
  (SQLite в памяти).
- Отсечка: старое сообщение → `OLD`; сообщение из очереди повторов и `--from-rowid` — не отсекаются.
- Частота уведомлений: одна причина дважды за 6 часов → одно уведомление; восстановление → одно.
- Отправка уведомлений — за трейтом `Notifier`, в тестах — запись в вектор.
- `cargo test`, `cargo clippy` — без ошибок.

README: команды `log` и `status`, `notify_created`, раздел «Как проверить, что сообщение заведено»; убрать
ограничение «если вы внесли такую же вручную — получится два экземпляра» в пользу Б2.

## 4. Порядок запуска

1. Влить и задеплоить PR бухгалтерии (Б1, Б2).
2. Собрать приложение с П1–П4, `make install`, `family-messages-sync setup` (токен `transactions:write`; для `init`
   один раз нужен `write` или категории `AUTO_EXPENSE` / `AUTO_INCOME`, созданные вручную).
3. **Сухой прогон по истории.** `show 50` → найти ROWID SMS двухнедельной давности →
   `run --dry-run --from-rowid N`. Ожидается: почти все SMS — «ДУБЛЬ … уже внесён вручную»; строки `DRY` — покупки,
   которые не внесли, или расхождение суммы, счёта или даты. Разобрать каждую `DRY`, при необходимости поправить
   `accounts` и правила.
4. `make fda`, `make agent`. Первый запуск только запоминает позицию.
5. Две недели в работе, ежедневно — `family-messages-sync status`, раз в неделю — `log 100`, разбор операций
   `[АВТО: проверить]` (на сайте или «разберём автоматические» в Claude).

## 5. Сценарии проверки

| # | Сценарий | Ожидается |
| --- | --- | --- |
| С1 | Покупка внесена через Claude до SMS (или в течение `delay_minutes`) | Операция не создаётся; в `log` — «найдена ручная» со ссылкой |
| С2 | Покупка не внесена | Через ~10–15 мин операция `AUTO_EXPENSE`, `[АВТО: проверить]`; уведомление; в `log` — «создано» |
| С3 | SMS уже заведено, потом «кофе 60 бат» в Claude | Claude находит операцию из SMS, дополняет её и говорит об этом; вторая не появляется |
| С4 | Две одинаковые покупки за день, одна внесена вручную | Одна — «найдена ручная», вторая — «создано» |
| С5 | Операция из SMS исправлена в форме на сайте, затем `run --from-rowid` по тому же SMS | Заметка `[sms:…]` на месте; «уже отправлено», без дубля |
| С6 | OTP от банка | Не заводится, в журнале `IGNORED` без текста |
| С7 | Неизвестный формат | `UNRECOGNIZED`, строка в `unparsed.log` |
| С8 | Бухгалтерия недоступна или Wi-Fi выключен | Уведомление об остановке; после восстановления всё догоняется, уведомление «снова работает» |
| С9 | Токен отозван | Уведомление «401»; после `set-token` догоняется |
| С10 | Mac спал ночь | Утром SMS за ночь заведены с датами из текста |
| С11 | Пересборка и `make install` без `make fda` | Уведомление о доступе к `chat.db` |
| С12 | Перевод на свой счёт (два SMS) | Расход и доход; при разборе — заменить переводом (известное ограничение) |
| С13 | Перевод внесён вручную до SMS | Оба SMS — «найдена ручная» |

## 6. Критерии готовности

- PR бухгалтерии влит: тест Б1 зелёный, `cargo test --workspace`, запись «Что нового» на трёх языках.
- В приложении — П1–П4 с тестами, README обновлён.
- Сценарии С1–С11 пройдены на Mac владельца.
- За две недели: ни одного дубля, которого нет в «известных ограничениях», и ни одной молчаливой остановки дольше
  часа бодрствования Mac.

## 7. Вне рамок

Делается по `docs/tz.md` и шагу 4 бухгалтерии после пробного запуска:

- `external_ref`, `source`, `needs_review` в бухгалтерии, значок «SMS» и фильтр «Не проверено» на сайте;
  сопоставление с ручными операциями на сервере вместо клиента; право `autoimport:write`.
- Дополнение операции из SMS при ручном вводе на сайте (быстрый ввод).
- Сопоставленная ручная операция не помечается в бухгалтерии: связь видна только в журнале на Mac.
- Мягкое удаление: удалённая на сайте операция из SMS после `run --from-rowid` создастся снова.
- Цепочка остатков, сверка с остатком счёта, «Входящие», локальный веб-интерфейс, документ настроек.
- Подпись бинарника, ротация логов.

Итог пробного запуска — список реальных форматов SMS, доля сопоставленных с ручными, случаи дублей. По нему
уточняются ключ `external_ref` (`docs/tz.md` 7.2 и `docs/group-1.md` 4.1 расходятся) и порядок этапов.
