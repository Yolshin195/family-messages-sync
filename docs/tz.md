# ТЗ: сообщения банка → семейная бухгалтерия

21.10.2026 · версия 3

Банковские SMS приходят на Mac. Локальное приложение превращает их в операции в
[family-budget](https://github.com/Yolshin195/family-budget) или прикрепляет к операциям, которые семья уже
внесла сама. Цель — не вводить суммы и счета руками и не забывать покупки.

Тексты SMS не покидают Mac. Что брать, как читать и как заполнять операцию, человек настраивает в приложении у
себя. На сервер уходят только операции с отметкой «не проверено» и короткие отметки «ждёт разбора» без текста.
Настройки хранятся на сервере как копия, чтобы не потерять их и перенести на другой Mac. Про непроверенное раз в
день спрашивает Claude.

| Часть | Где | Что это |
| --- | --- | --- |
| **A1. Читатель `family-messages-reader`** | этот репозиторий | Маленькая программа с Full Disk Access. Копирует сообщения отправителей-банков из `chat.db` в локальную очередь. Без сети и без разбора. Меняется редко |
| **A2. Приложение `family-messages-sync`** | этот репозиторий | Фоновый процесс с интерфейсом в браузере на `127.0.0.1`. Отсеивает лишнее, читает сумму и счёт, заполняет операцию, отправляет её через API, хранит копию настроек на сервере. Full Disk Access ему не нужен, поэтому обновляется свободно |
| **B. Фича `autoimport`** | family-budget | Узкий API для приложения: завести операцию из SMS или прикрепить SMS к ручной, отметки «ждёт разбора», копия настроек, подсказки. Фильтры в «Операциях». Инструменты MCP для Claude |

A1 и A2 связаны локальным файлом SQLite (раздел 9), A2 и B — HTTP API (раздел 10). Все три части можно делать
параллельно.

Предыдущая программа — `accounting-messages-sync`: правила-regex в `config.json`, старый Accounting API.
Из неё переносится: запрос к `chat.db`, текст из `attributedBody`, даты Apple, курсор по `ROWID`, Keychain,
запуск через launchd, `make deploy`, инструкции по Full Disk Access.

Схемы экранов версии 1: https://claude.ai/artifact/LYXNh5U5bpQGuTMLwruyej. Для версии 3 их нужно перерисовать:
настройка переехала в локальное приложение.

### Что изменилось с версии 2

| Было в v2 | Стало в v3 | Почему |
| --- | --- | --- |
| Mac отправляет сообщения банков, разбор на сервере | Разбор на Mac. На сервер уходят только операции и отметки «ждёт разбора» без текста | Тексты SMS (остатки, номера счетов, нераспознанное) серверу не нужны. Меньше данных на сервере — меньше риск |
| Одна программа на Mac | Читатель (Full Disk Access, без сети) и приложение (сеть и интерфейс, без доступа к диску) | Читатель почти не меняется, доступ не слетает. Процесс с доступом ко всему диску не держит сеть и веб-сервер |
| «Правила» означали сразу и отсев, и разбор, и категории | Три отдельные вещи: **отсев** (что брать), **форматы** (как читать), **заполнение** (что ставить в поля) | Слово «правила» путало |
| Экраны настройки в бухгалтерии | Настройка — в локальном приложении. На сервере только копия | Живая проверка идёт на сообщениях, а они есть только на Mac |
| «Входящие» на сервере с текстами SMS | «Входящие» на Mac. На сервер — отметка: отправитель, время, причина, сумма, если разобрана | Claude видит, что есть неразобранное. Текст уходит, только если нажать «Отправить Claude» у сообщения |
| Склейка только при единственном кандидате | Ближайший кандидат по дате и времени; ручная запись после SMS дополняет операцию из SMS автоматически | Одинаковые суммы в один день — норма (реальные данные) |
| Сверка остатка — этап 5, на сервере | Цепочка остатков и сверка с бухгалтерией — этап 2, на Mac. Остаток на сервер не уходит | По реальным данным это главный способ поймать забытую покупку |
| Токен Mac `inbox_ingest:write` | Токен Mac `autoimport:write` и чтение справочников | Заводит только операции из SMS и меняет только свои непроверенные |

Из версии 2 без изменений: метки форматов, любые поля в заполнении, значения по умолчанию, места по продавцу,
подсказки по истории, отметка «не проверено», вопрос Claude по вечерам.

## 1. Решение

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| v2. Mac отправляет сообщения банков, разбор и настройки на сервере | Один интерфейс в бухгалтерии, настройка с телефона. Claude видит тексты | Тексты банковских SMS хранятся на сервере: остатки, номера счетов, нераспознанное, реклама банка |
| **v3. Читатель и локальное приложение; на сервере операции и копия настроек (выбрано)** | Тексты SMS не покидают Mac. Живая проверка на всей истории SMS. Сервер меняется меньше: нет разбора и экранов настройки. Процесс с доступом к диску крошечный и не меняется | Второй интерфейс, локальный: настройка только на Mac. Claude не видит текст нераспознанного. Движок разбора живёт на Mac: серверным источникам (почта, Telegram) придётся подключать его как крейт |

Почему сняты возражения против разбора на Mac из версии 2:

1. **Нераспознанное не теряется.** На сервер уходит отметка «ждёт разбора» без текста. Её видят счётчик в
   «Операциях» и Claude.
2. **Разборщик один**, на Mac. Живая проверка работает там же, где лежат сообщения, и на всей их истории.
3. **Изменение действует сразу**: настройку меняют на том же Mac, где идёт разбор.
4. **Право токена узкое**: только операции из SMS (10.1).
5. **Full Disk Access не слетает**: доступ у читателя, а меняется приложение.

На сервере остаётся то, для чего нужны его данные: склейка с ручными операциями (только сервер знает о них),
подсказки по истории и вопрос Claude.

Процессы разделены по правам:

| Процесс | Full Disk Access | Сеть | Как часто меняется |
| --- | --- | --- | --- |
| Читатель | да | нет | Редко: когда macOS меняет схему `chat.db` |
| Приложение | нет | к бухгалтерии и на `127.0.0.1` | Свободно: отсев, форматы, заполнение, интерфейс |

## 2. Термины

| Термин | Значение |
| --- | --- |
| Сообщение | SMS или iMessage от отправителя-банка, скопированное читателем в очередь |
| Очередь | Файл SQLite `spool.db`. В него пишет читатель, приложение только читает |
| **Отсев** | Что брать и что выбрасывать: список отправителей-банков (его исполняет читатель) и список «Пропускать» — коды подтверждения, реклама, служебные SMS (исполняет приложение). Раздел 4 |
| **Формат** | Как прочитать текст одного вида: отправитель, образец с метками (`{amount}`, `{account}`…) или regex, тип операции. «KBank: списание». Раздел 5 |
| **Заполнение** | Что поставить в поля операции: значения по умолчанию и исключения «если … то …». Раздел 6 |
| Номер карты | Последние 4 цифры карты или счёта из текста (`X-5019` → `5019`), привязанные к счёту бухгалтерии |
| Не проверено | Операция на сервере заведена из SMS без ручной пары, категорию человек не подтвердил |
| Ждёт разбора | Отметка на сервере о сообщении, из которого операция не получилась, или о пропуске в цепочке остатков. Без текста |
| Склейка | Сервер нашёл ручную операцию с тем же счётом и суммой и прикрепил к ней SMS вместо создания новой |
| Копия настроек | Документ JSON: отправители, «Пропускать», форматы, заполнение, номера карт. Хранится на сервере с версией |

## 3. Путь сообщения

```
Читатель (launchd, раз в 30 с)
  chat.db → новые строки → отправитель-банк? → копия строки как есть в spool.db
Приложение (launchd, постоянно)
  spool.db → новые строки → текст → «Пропускать»? → формат → сумма, счёт, остаток
           → заполнение (по умолчанию, исключения, место) → проверки → цепочка остатков
           → POST /api/autoimport/transactions → сервер: дубль? ручная пара? → склеить или завести
           → или «Входящие» на Mac + POST /api/autoimport/pending (без текста)
Claude (раз в день)
  операции «не проверено» + отметки «ждёт разбора» → вопрос → правка операций
```

Статусы сообщения в приложении:

| Статус | Значение | Во «Входящих» |
| --- | --- | --- |
| `MATCHED` | Сервер прикрепил SMS к ручной операции | нет |
| `CREATED` | Ручной пары не было, операция заведена. Отметка «не проверено» — у самой операции на сервере | нет |
| `CONFIRMED` | Заведено вручную: в приложении, через Claude или на сайте по отметке | нет |
| `QUEUED` | Разобрано, сервер недоступен. Уйдёт при следующей попытке | нет |
| `PENDING` | Операция не получилась, причина в `reason`. На сервере отметка «ждёт разбора» | **да** |
| `DROPPED` | Отсеяно списком «Пропускать» | нет |
| `DISMISSED` | Пропущено вручную | нет |

Причины `PENDING`: `UNRECOGNIZED` — формат не подошёл или сумма не разобралась; `ACCOUNT_UNKNOWN`;
`CURRENCY_MISMATCH`; `TRANSFER_TARGET_MISSING`; `HAS_LINK`; `DUPLICATE_TEXT`; `ASK` — так велит заполнение;
`REJECTED` — сервер отказал (7.1). Отдельная отметка без сообщения — `BALANCE_GAP` (7.4).

**Что уходит на сервер:**

| Данные | На сервер |
| --- | --- |
| Текст SMS | Нет. Только по кнопке «Отправить Claude» у одного сообщения |
| Остаток по счёту из SMS | Нет. Сверка с бухгалтерией — на Mac (7.4) |
| Номер карты | Нет. Сопоставление на Mac. В отметке `ACCOUNT_UNKNOWN` — 4 цифры, чтобы было понятно, о какой карте речь |
| Операция: дата, время SMS, счёт, сумма, категория, место, «для кого», описание, `external_ref` | Да |
| Отметка «ждёт разбора»: отправитель, время, причина; сумма и счёт, если известны | Да |
| Настройки: отправители, «Пропускать», форматы, заполнение, номера карт | Да, копия |
| Личная переписка | Никогда: читатель её не копирует |

## 4. Отсев

Отсев отвечает на вопрос «брать ли это сообщение вообще». У него два уровня.

### 4.1. Отправители-банки

Подстроки в отправителе без учёта регистра: `kbank`, `k plus`, `kplus`. Список выбирает человек на экране
«Отправители» (8.2). Читатель копирует в очередь только эти сообщения. Личная переписка не попадает даже в
очередь.

### 4.2. «Пропускать»

Сообщения банка, которые не являются операциями: коды подтверждения, реклама, «выписка готова». Приложение
выбрасывает их до разбора (`DROPPED`). Они не уходят никуда и не пишутся в лог.

| Поле | Смысл |
| --- | --- |
| Название | «KBank: реклама» |
| Отправитель | Подстрока; пусто — любой банк из списка |
| Текст | Подстрока или regex (режим `CONTAINS` / `REGEX`, без учёта регистра) |
| Включено | Переключатель |

Встроенный набор «Коды подтверждения» ставится при первой настройке и редактируется как обычный: `(?i)\botp\b`,
`(?i)one[- ]time password`, `(?i)verification code`, `(?i)код подтверждения`, `(?i)одноразов\w* код`,
`(?i)никому не сообщайте`, `รหัส\s*OTP`, `รหัสยืนยัน`.

Сообщение банка, которое не попало в «Пропускать» и не подошло ни к одному формату, **не выбрасывается**, а
попадает во «Входящие» (`UNRECOGNIZED`). Так новая операция банка не потеряется молча.

## 5. Форматы

Формат описывает один вид сообщения, например «KBank: списание». Форматы проверяются по порядку, побеждает
первый подходящий. Отключённые пропускаются. Формат только читает текст: тип операции, сумму, счёт, остаток.

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| Название | да | «KBank: списание» |
| Отправитель | нет | Подстрока в отправителе без учёта регистра (`kbank`). Пусто — любой |
| Синтаксис | да | `TEMPLATE` — образец с метками (по умолчанию); `REGEX` — регулярное выражение для сложных случаев |
| Образец | да | Текст образца или regex, до 1000 символов |
| Тип операции | да | `EXPENSE` расход, `INCOME` доход, `REFUND` возврат, `TRANSFER` перевод |
| Порядок, включён | да | Позиция в списке, переключатель |

Образец лучше делать коротким: слово, по которому узнаётся операция, сумма, номер карты и остаток. Чем меньше в
образце постоянного текста, тем меньше шанс, что банк изменит его и формат перестанет совпадать.

### 5.1. Образец с метками

Образец — это текст сообщения, где изменяемые части заменены метками. Правила сопоставления:

- регистр не важен;
- любая последовательность пробелов совпадает с любой другой;
- остальной текст сравнивается буквально, спецсимволы экранируются;
- образец ищется внутри сообщения, а не сравнивается с ним целиком;
- каждая метка, кроме `{*}`, встречается не больше одного раза;
- метка `{amount}` обязательна.

| Метка | Что совпадает | Пример |
| --- | --- | --- |
| `{amount}` | Сумма операции: цифры, разделители тысяч (`,` пробел NBSP `'`), дробная часть через `.` или `,` | `11,088.02`, `1 234,56` |
| `{balance}` | Остаток после операции, формат как у суммы. Нужен для цепочки остатков (7.4) | `3,156.76` |
| `{currency}` | Валюта: код или символ. Сопоставляется по таблице 5.4 | `Baht`, `฿`, `THB`, `₽`, `руб.` |
| `{account}` | Номер карты или счёта (непробельные символы, в конце не меньше 4 цифр) | `X-5019`, `*1234`, `MIR-1234` |
| `{merchant}` | Продавец или контрагент: минимально возможный текст до следующей части образца, в конце образца — до конца строки | `X-8842`, `7-ELEVEN SUKHUMVIT` |
| `{date}` | Дата: `d/m/yy`, `d.m.yyyy`, `yyyy-mm-dd`; разделители `/ . -`. Только для сопоставления | `20/10/26` |
| `{time}` | Время `h:mm` или `h:mm:ss`. Только для сопоставления | `22:31` |
| `{*}` | Любой текст, минимально возможный. Можно использовать несколько раз | |

Образец компилируется в regex крейта `regex`. В форме видно, во что он скомпилировался: так удобнее перейти на
синтаксис `REGEX`.

Синтаксис `REGEX` — это regex крейта Rust (без lookahead и lookbehind). Именованные группы называются так же, как
метки: `amount`, `balance`, `currency`, `account`, `merchant`, `date`, `time`. Группа `amount` обязательна.
`REGEX` нужен, когда одна операция пишется разными словами: у старой программы доход узнавался по `deposit`,
`received`, `transfer in` или `credit`.

### 5.2. Готовые форматы KBank

| Сообщение | Образец | Тип |
| --- | --- | --- |
| `20/10/26 22:31 A/C X-5019 Withdrawal 89.00 Outstanding Balance 3,156.76 Baht.` | `A/C {account} Withdrawal {amount} Outstanding Balance {balance}` | `EXPENSE` |
| `20/09/26 11:44 A/C X-5019 Deposit 11,088.02 Outstanding Balance 12,282.25 Baht.` | `REGEX`: `(?i)A/C (?P<account>\S+) (?:deposit\|received\|transfer in\|credit)\w*\s+(?P<amount>\d[\d,]*\.\d{2})(?:.*?Outstanding Balance (?P<balance>\d[\d,]*\.\d{2}))?` | `INCOME` |
| `21/10/26 10:54 A/C X-5019 transferred 500.00 Baht to A/C X-8842 Outstanding Balance 2,299.76 Baht.` | `A/C {account} transferred {amount} {currency} to A/C {merchant} Outstanding Balance {balance}` | `EXPENSE` (заполнение может сделать из него перевод между своими счетами, 6.2). `{merchant}` — счёт получателя |

Формат кодов подтверждения не нужен: их выбрасывает «Пропускать» (4.2).

Библиотека готовых форматов лежит в крейте `core` (`presets.rs`). В приложении есть кнопка «Добавить готовые»:
выбрать банк, и его форматы добавляются в конец списка. Каждый готовый формат покрыт тестом на реальных SMS
(суммы и номера в тестах изменены) и на примерах из тестов старой программы. Новые банки добавляются pull
request'ом.

### 5.3. Формат из сообщения

«Создать формат» у нераспознанного сообщения заполняет образец его текстом и заменяет части на метки:

- даты → `{date}`, время → `{time}`;
- токены вида `X-5019`, `*1234` → `{account}`;
- число после слов balance / остаток / баланс / ยอดคงเหลือ → `{balance}`;
- первое из оставшихся чисел с дробной частью → `{amount}`;
- остальные числа → `{*}`.

Человек сокращает образец до нужного и сразу видит результат живой проверки.

### 5.4. Разбор значений

**Сумма** (`{amount}`, `{balance}`) → `Decimal`:

1. Убрать пробелы, NBSP, узкие пробелы и апострофы.
2. Если есть и `,`, и `.`, дробный разделитель — тот, что правее. Второй удаляется.
3. Если разделитель один и встречается один раз, а после него 1–2 цифры, это дробная часть. Иначе это разделитель
   тысяч.
4. Если сумма 0 или не число → `PENDING` / `UNRECOGNIZED` («не удалось разобрать сумму»). Не разобрался остаток —
   операция заводится, цепочка остатков для неё пропускается.

| Текст | Значение |
| --- | --- |
| `8,195.25` | 8195.25 |
| `1 234,56` | 1234.56 |
| `60.00` | 60 |
| `1,000` | 1000 |
| `1.234.567` | 1234567 |
| `1.5` | 1.5 |

**Валюта** (`{currency}`) сопоставляется с кодом в таком порядке:

1. Код или символ валюты из справочника проекта (кэш с сервера).
2. Встроенные синонимы: `Baht`, `บาท`, `฿` → THB; `руб`, `руб.`, `р.`, `₽` → RUB; `$` → USD; `€` → EUR.

Валюта не распозналась или не совпадает с валютой счёта → `CURRENCY_MISMATCH`. Покупки в другой валюте
бухгалтерия пока не поддерживает (ТЗ бухгалтерии, этап 8). Если в образце нет `{currency}`, считается, что
операция в валюте счёта.

**Счёт** (`{account}`): из текста берутся цифры, последние 4 из них образуют номер (`X-5019` → `5019`). Номер
ищется в таблице «Карты» (6.1). Не нашёлся или в тексте нет `{account}` → счёт из заполнения. Нет и там →
`ACCOUNT_UNKNOWN`. На строке во «Входящих» есть «Привязать 5019 к счёту…», после этого сообщение обрабатывается
повторно.

**Дата и время операции** — время получения сообщения по часовому поясу Mac. Так работала старая программа: SMS
о списании приходит через секунды после операции. Дата из текста не разбирается, поэтому нет ни порядка дат, ни
годов буддийской эры. Время получения уходит на сервер вместе с операцией: по нему выбирается ручная пара (7.3).

## 6. Заполнение

Формат даёт факты: тип, сумму, счёт, остаток, контрагента. Заполнение решает, что поставить в остальные поля
операции, если ручной пары не нашлось. Любое поле операции можно задать по умолчанию.

### 6.1. По умолчанию

| Поле | По умолчанию |
| --- | --- |
| Счёт | По таблице «Карты»: номер → счёт (`5019` → «K-Bank»). Плюс счёт для SMS без номера карты |
| Категория расхода и возврата | «Нераспределённые расходы» (создаётся при настройке, 10.1) |
| Категория дохода | «Нераспределённые доходы» |
| Для кого | Пусто — для всех |
| Описание | Шаблон с подстановками `{merchant}`, `{account}`, `{format}`; пусто — название формата («KBank: списание») |
| Проверять | Включено: операция получает отметку «не проверено» |
| Действие | `CREATE` — заводить. `ASK` — ничего не заводить без человека, всё во «Входящие». Удобно первую неделю |

### 6.2. Исключения

Исключение — «если … то …»: условия и поля, которые надо поставить вместо значений по умолчанию. Исключения
проверяются по порядку, побеждает первое подходящее. Нужно хотя бы одно условие.

| Условие | Как проверяется |
| --- | --- |
| Тип операции | Равен (`EXPENSE` / `INCOME` / `REFUND` / `TRANSFER`) |
| Формат | Сообщение разобрано этим форматом |
| Счёт | Счёт, найденный по номеру карты, равен заданному |
| Контрагент | `{merchant}` содержит текст или совпадает с regex (режим `CONTAINS` / `REGEX`, без учёта регистра) |
| Текст | Весь текст сообщения содержит подстроку или совпадает с regex |
| Сумма | от / до, включительно |

Что может поставить исключение: тип (расход → перевод), счёт, счёт зачисления, место, категорию, «для кого»,
описание с переводами ru/en/th, «Проверять» и действие (`CREATE`, `ASK`, `SKIP` — пропустить).

Примеры:

| Если | То |
| --- | --- |
| Контрагент `X-8842` (карта близкого человека) | Категория «Переводы близким», для кого — этот человек, описание «Перевод на мелкие расходы», не проверять |
| Контрагент `X-1234` (свой накопительный) | Тип «перевод», счёт зачисления «Накопительный», не проверять |
| Сумма от 10 до 10, формат «KBank: списание» | Категория «Парковка», проверять |

Исключение не меняет **факты из SMS**: сумму, дату, валюту и счёт, найденный по номеру карты. Счёт из исключения
используется, только когда по номеру карты счёт не нашёлся.

Списки счетов, категорий, мест и людей для форм приложение берёт с сервера и держит в кэше.

### 6.3. Места по продавцу

В family-budget у места уже есть варианты написания (`aliases`), категория и счёт. Если в SMS есть продавец,
он сравнивается с названиями и вариантами написания мест из кэша. Вариант должен содержаться в `{merchant}`,
побеждает самый длинный. Место подставляет свою категорию (у магазина без категории — категорию сети). Счёт места
не используется: счёт из SMS точнее. Операция с найденным местом считается проверенной.

Для KBank это не сработает: продавца в его SMS нет. Места пригодятся банкам, которые пишут продавца, и будущим
источникам вроде слипов.

### 6.4. Порядок заполнения

1. Факты из SMS: тип из формата, сумма, время, валюта, счёт по номеру карты.
2. Первое подходящее исключение: его непустые поля и действие.
3. Место по продавцу, если исключение не задало место и категорию.
4. Пустые поля — по умолчанию.

Заполнение работает только для операции без ручной пары. Если сервер нашёл пару (7.3), ручная операция не
меняется.

### 6.5. Подсказки по истории

Когда у операции нет ни продавца, ни подходящего исключения (обычный случай для KBank), единственная зацепка —
счёт и сумма. Сервер ищет проверенные операции с тем же счётом и той же суммой за последние 90 дней и отдаёт до
трёх самых частых сочетаний «категория + место»: «60 ฿ с K-Bank: 5 раз “Кофе и чай · Café Amazon”, 1 раз “Кофе и
чай · One To Two”».

- Подсказки только показываются и сами ничего не заводят: одинаковые суммы бывают у разных покупок.
- Видны кнопками в одно нажатие в форме «Завести» приложения, в строке непроверенной операции на сайте и в
  `list_review` у Claude.
- Считает их сервер при показе: история операций есть только там.

## 7. Обработка

### 7.1. Алгоритм

Разбор — чистая функция крейта `core` без ввода-вывода:
`process(message, settings, reference, recent) → Outcome`. `settings` — отсев, форматы, заполнение, карты;
`reference` — кэш справочников с сервера; `recent` — недавние сообщения для дублей и цепочки остатков. Функция
покрыта тестами без сети и БД.

1. Совпало с «Пропускать» → `DROPPED`.
2. Найти первый включённый формат, у которого подходит отправитель и совпадает образец. Не нашёлся →
   `PENDING` / `UNRECOGNIZED`.
3. Извлечь поля (5.4). Не разобралась сумма → `PENDING` / `UNRECOGNIZED`.
4. Тот же текст от того же отправителя за последние сутки → `PENDING` / `DUPLICATE_TEXT` (7.2).
5. Найти счёт по номеру карты, заполнить остальное (6.4). Действие `SKIP` → `DROPPED`. Действие `ASK` →
   `PENDING` / `ASK`.
6. Проверки, каждая → `PENDING` со своей причиной:
   - счёта нет → `ACCOUNT_UNKNOWN`;
   - валюта не совпадает со счётом → `CURRENCY_MISMATCH`;
   - у перевода нет счёта зачисления → `TRANSFER_TARGET_MISSING`;
   - в тексте ссылка (`http`, `www.`, домен) → `HAS_LINK`. Банки не присылают ссылок в уведомлениях об
     операциях, а поддельные SMS от имени банка присылают.
7. Проверить цепочку остатков (7.4).
8. Отправить в `POST /api/autoimport/transactions` с `external_ref = "imessage:<guid>"`, временем получения и
   заполненными полями. Ответ сервера:
   - `MATCHED` — нашлась ручная пара (7.3), ручная операция не изменилась;
   - `CREATED` — пары нет, операция заведена с отметкой «не проверено» по полю «Проверять»;
   - `DUPLICATE` — операция с этим `external_ref` уже есть (второй Mac, повтор после сбоя) → статус той операции;
   - `REJECTED` — отказ валидации (счёт или категория в архиве) → `PENDING` / `REJECTED` с текстом ошибки;
   - сеть или `5xx` → `QUEUED`, повтор на следующем проходе.
9. Для `PENDING` — отметка на сервер (`POST /api/autoimport/pending`), без текста.

Разобранные поля, формат, исключение и итог сохраняются в `app.db`. Так любое решение можно объяснить: «формат
“KBank: списание”, склеено с “Капучино в Café Amazon”».

### 7.2. Дубли

- **Точные.** На Mac ключ — `guid` сообщения: одна строка очереди обрабатывается один раз. На сервере уникален
  `(project_id, external_ref)`. При iCloud-синхронизации у сообщения одинаковый `guid` на всех Mac, поэтому два Mac
  с одним Apple ID дают одну операцию: второй получает `DUPLICATE`.
- **То же SMS под другим `guid`.** Полностью одинаковый текст от того же отправителя за сутки. В SMS KBank есть
  остаток, а он после каждой операции свой: две настоящие покупки по 89 ฿ подряд различаются остатком. Поэтому
  одинаковый текст — это почти наверняка одно SMS, пришедшее дважды. Оно уходит во «Входящие», а не выбрасывается:
  решает человек.
- **Сбой посередине.** Операция создана, а ответ не дошёл → сообщение остаётся `QUEUED`, повтор получает
  `DUPLICATE` и привязывает существующую операцию.

### 7.3. Склейка с ручными операциями

Семья вносит покупки фразой или фото чека через Claude и на сайте — с категориями, позициями и «для кого». По
реальным данным так внесены все операции. SMS о той же покупке не должно создавать вторую операцию, а должно
подтвердить, что запись есть. Склейку делает сервер: только он знает о ручных операциях.

**Сначала ручная, потом SMS.** Кандидат на пару:

- тот же счёт и тот же вид (расход, доход, перевод с этого счёта);
- та же сумма до копейки;
- дата отличается не больше чем на 2 дня (настройка);
- к операции ещё не прикреплено SMS (`external_ref` пуст).

Из кандидатов берётся ближайший: сначала по дате, затем по времени создания операции относительно времени SMS.
Одинаковые кандидаты для бухгалтерии равноценны, поэтому спрашивать человека не нужно. Пример: два SMS по 89 ฿ и
две ручные записи по 89 ฿ — первое SMS берёт одну, второе — оставшуюся.

Найдена пара → операции ставится `external_ref`, в списке у неё появляется отметка «SMS». Остальные поля и
`source` не меняются, отметка «не проверено» не ставится. Ответ `MATCHED`.

**Сначала SMS, потом ручная.** SMS пришло на кассе, а запись через Claude сделана через 10 минут. Операция из SMS
к этому времени уже заведена с отметкой «не проверено». Когда создаётся ручная операция (сайт, MCP), сервис ищет
непроверенную операцию из SMS с тем же счётом и суммой в тот же или соседний день и **дополняет её** вместо
создания новой: переносит категории, позиции чека, место, «для кого», описание и снимает отметку «не проверено».

- В MCP ответ `add_expense` / `add_income` говорит: «дополнил операцию из SMS 10:59». Параметр `new: true` —
  создать отдельную операцию, если человек говорит, что это другая покупка.
- На сайте — тост «Дополнил операцию из SMS 10:59 · Это другая покупка». Кнопка разделяет их обратно.

### 7.4. Цепочка остатков и сверка

В SMS KBank есть остаток после операции, и остатки образуют цепочку:

```
20/10 22:27  Withdrawal 80.00   Balance 3,245.76
20/10 22:31  Withdrawal 89.00   Balance 3,156.76   3 245.76 − 89 = 3 156.76 ✓
21/10 10:27  Withdrawal 115.00  Balance 2,952.76   3 067.76 − 115 = 2 952.76 ✓ (предыдущее SMS — 22:32)
```

- **Разрыв цепочки.** Остаток прошлого SMS этого счёта ± сумма не равен новому остатку → по счёту прошла операция
  без SMS (например, платёж, о котором пришёл только push K PLUS). Приложение отправляет отметку
  `BALANCE_GAP` с суммой разрыва и счётом: «Пропущена операция на 120 ฿ по K-Bank между 10:31 и 10:54». Её видит
  Claude и может завести операцию по ответу человека.
- SMS могут прийти не по порядку. Разрыв фиксируется, только если он не закрылся за 10 минут.
- **Сверка с бухгалтерией.** После прохода, когда очередь отправки пуста, приложение берёт остаток счёта с
  сервера и сравнивает с остатком из последнего SMS. «Сводка» показывает: «K-Bank: банк 2 239.76, бухгалтерия
  2 239.76 ✓». Расхождение — предупреждение в «Сводке» и уведомление macOS.
- Остаток из SMS на сервер не уходит. Сравнение делается на Mac.

### 7.5. Повторная обработка

- «Обработать заново» у одного сообщения во «Входящих».
- «Применить к подходящим» после сохранения формата, исключения или настройки по умолчанию. Действует на:
  - сообщения во «Входящих» за последние 90 дней;
  - сообщения в `CREATED` за последние 90 дней, чья операция на сервере ещё «не проверено»
    (`GET /api/autoimport/transactions?refs=…`). У таких операций меняются категория, место, «для кого» и
    описание (`PUT /api/autoimport/transactions/{external_ref}`). Тип и счета не меняются: такие операции
    показываются в предпросмотре отдельным списком со ссылкой на сайт.

  Сначала предпросмотр («будет заведено 12, уточнена категория у 7, во входящих останется 3»), потом
  подтверждение.
- Проверенные и склеенные операции, сообщения в `CONFIRMED`, `DROPPED`, `DISMISSED` не трогаются.

### 7.6. Отметки, разобранные не на Mac

Отметку «ждёт разбора» можно закрыть на сайте или через Claude: завести операцию по ней или пропустить. Приложение
раз в проход спрашивает `GET /api/autoimport/pending?resolved_since=…` и переводит такие сообщения в `CONFIRMED`
или `DISMISSED`. Закрытие на Mac удаляет отметку (`DELETE /api/autoimport/pending/{external_ref}`).

## 8. Локальное приложение (A2)

### 8.1. Устройство

- Rust, Axum, Askama, htmx — тот же стек, что у family-budget. Стили — собранный CSS family-budget, чтобы
  приложение выглядело так же.
- Постоянный процесс под launchd (12.3). Внутри — проход разбора раз в 30 секунд и веб-сервер на
  `127.0.0.1:8765` (порт меняется в настройках).
- `family-messages-sync open` открывает интерфейс в браузере. Значок в строке меню — этап 5.
- Язык интерфейса — как у пользователя в бухгалтерии. Тексты в i18n-файле, в v1 ru и en, th позже.
- Интерфейс доступен только на этом Mac: сообщения тоже есть только здесь.

### 8.2. Экраны

| Экран | URL | Что делает |
| --- | --- | --- |
| Сводка | `/` | Читатель: последний проход, ошибка (нет Full Disk Access — инструкция и путь к бинарнику). Сервер: связь, проект, пользователь, версия копии настроек. Остатки: банк и бухгалтерия по каждому счёту (7.4). Сегодня: склеено, заведено, не проверено, во «Входящих», в очереди |

Действия: «Завести», «Пропустить», «Обработать заново», «Создать формат», «Создать исключение», «Добавить в “Пропускать”», «Привязать 5019 к счёту…», «Отправить Claude» |

Форматы, исключения и строки «Пропускать» удаляются без «Вы уверены?», с тостом «Отменить», как в family-budget.

### 8.3. Копия настроек на сервере

- Рабочая копия — в `app.db`. После каждого изменения приложение отправляет документ целиком:
  `PUT /api/autoimport/config` с `If-Match: <версия>`.
- Раз в 5 минут и при открытии интерфейса — `GET` с `If-None-Match`. Почти всегда `304`. Новая версия с сервера
  (настройки меняли на другом Mac) применяется сразу, кроме списка отправителей (ниже).
- Конфликт (`412`): настройки меняли на двух Mac одновременно. Приложение показывает обе версии и предлагает
  взять серверную или свою. Молча ничего не перезаписывается.
- **Отправители-банки с сервера на этом Mac применяются только после подтверждения здесь**: «В копии настроек
  отправители kbank, k plus. Читать их на этом Mac?». Иначе подменённая копия на сервере могла бы заставить
  читатель копировать чужую переписку.
- Сервер документ не разбирает: проверяет размер (≤ 256 КБ), что это JSON, и номер схемы (11.3).
- Перенос на другой Mac: установить, `setup` с тем же проектом, «Восстановить с сервера», подтвердить
  отправителей.

### 8.4. Безопасность интерфейса

Локальный веб-сервер доступен любой программе и любой открытой вкладке браузера на этом Mac, поэтому:

- слушает только `127.0.0.1`;
- проверяет заголовок `Host`: только `127.0.0.1:<порт>` и `localhost:<порт>`. Это защита от DNS rebinding, когда
  чужая страница в браузере ходит на локальный порт;
- вход по одноразовой ссылке: `family-messages-sync open` открывает `http://127.0.0.1:8765/login?code=…`. Сервер
  ставит cookie `HttpOnly; SameSite=Strict`, код больше не действует;
- изменяющие запросы — только `POST` с CSRF-токеном, как в family-budget;
- автоэкранирование Askama: текст SMS не доверенный, `safe` не используется;
- CORS не включается.

## 9. Читатель (A1)

### 9.1. Что делает

Один проход и выход:

1. Открыть `~/Library/Messages/chat.db` только на чтение.
2. Прочитать `reader.json`: список отправителей-банков, `backfill_since`, срок хранения очереди.
3. Выбрать строки `message.ROWID > cursor`, `is_from_me = 0`, `JOIN handle`, по `ROWID`, не больше 1000. Поля:
   `ROWID`, `guid`, `text`, `attributedBody`, `date`, `handle.id`.
4. Для каждой строки обновить статистику отправителей (отправитель, число сообщений, дата последнего — без
   текста).
5. Строки, где отправитель содержит подстроку из списка (без учёта регистра), скопировать в очередь как есть, с
   сырым `attributedBody`. `INSERT OR IGNORE` по `ROWID`.
6. Сдвинуть курсор, удалить из очереди строки старше срока хранения (по умолчанию 90 дней), записать состояние
   прохода. Всё в одной транзакции очереди.

### 9.2. Насколько он «глупый»

Читателю дан доступ ко всему диску, поэтому в нём минимум кода (ориентир — 200 строк) и ничего лишнего:

- **нет сети**: в зависимостях нет HTTP-клиента, CI проверяет это `cargo tree`;
- **нет разбора**: текст из `attributedBody` достаёт приложение. Исправление разбора не требует новой сборки
  читателя;
- **нет фильтров**, кроме подстроки отправителя. «Пропускать» исполняет приложение;
- **нет настроек**, кроме `reader.json`, который пишет приложение;
- меняется только если macOS изменит схему `chat.db`.

Зависимости: `anyhow`, `rusqlite` (bundled), `serde`, `serde_json`.

### 9.3. Первый запуск и история

- Первый проход ставит курсор на текущий наибольший `ROWID` и ничего не копирует, как старая программа. После
  установки в бухгалтерию не вываливаются сотни старых SMS.
- Статистику отправителей первый проход собирает за последние 90 дней одним запросом с `GROUP BY`, чтобы на
  экране «Отсев → Отправители» сразу был выбор.
- История: приложение пишет в `reader.json` `backfill_since`. Следующий проход копирует сообщения
  отправителей-банков с этой даты (курсор не трогает), приложение очищает поле. Ручные операции за этот период
  склеятся (7.3): так можно проверить, что за прошлый месяц ничего не забыто.
- Новый отправитель в списке действует с текущего момента. Его прошлые сообщения — тоже через `backfill_since`.

### 9.4. Файлы

Каталог `~/Library/Application Support/family-messages-sync/`, права `0700`:

| Файл | Пишет | Читает | Что внутри |
| --- | --- | --- | --- |
| `reader.json` | приложение | читатель | `senders`, `backfill_since`, `retention_days` |
| `spool.db` | читатель | приложение (только чтение) | `messages(rowid PK, guid UNIQUE, sender, text, attributed_body, date_apple, copied_at)`, `senders(handle PK, total, last_date_apple)`, `state(key PK, value)`: курсор, время и ошибка последнего прохода |
| `app.db` | приложение | приложение | Раздел 11.1 |

SQLite в режиме WAL: читатель пишет, приложение читает одновременно.

### 9.5. Автозапуск

`~/Library/LaunchAgents/local.family-messages-reader.plist`:

- `ProgramArguments`: `[~/.local/bin/family-messages-reader]`;
- `RunAtLoad`, `StartInterval 30`;
- `ProcessType Background`;
- логи в `~/Library/Logs/family-messages-sync/reader.{out,err}.log`.

Во сне launchd не запускает читатель, после пробуждения первый проход забирает накопленное. Без Full Disk Access
проход пишет ошибку в `state` очереди и в `err.log` и повторяется через 30 секунд. «Сводка» приложения показывает
ошибку с инструкцией.

### 9.6. Full Disk Access и подпись

Full Disk Access выдаётся только `~/.local/bin/family-messages-reader`. Приложению он не нужен.

По опыту старой программы после пересборки macOS забывает доступ. Читатель пересобирается редко, но и тогда
доступ хочется сохранить. Если задан `CODESIGN_IDENTITY` (постоянный самоподписанный сертификат из «Связки
ключей»), `make install-reader` подписывает бинарник им. Тогда доступ должен переживать пересборку; проверить это
на практике на этапе 2. Без сертификата — после обновления читателя `make fda` заново, и `make` об этом напоминает.

## 10. Сервер (часть B, family-budget)

### 10.1. API для приложения

Новое право токена `autoimport:write` («Автоимпорт SMS с Mac», ru/en/th) плюс чтение справочников: счета (с
остатками), категории, места, люди, валюты — через существующие API. Пути `/api/autoimport/…`:

| Метод и путь | Действие |
| --- | --- |
| `GET /status` | Проект, пользователь токена, число непроверенных операций и отметок «ждёт разбора», версия копии настроек |
| `POST /setup` | Идемпотентно создаёт «Нераспределённые расходы» и «Нераспределённые доходы» с переводами, если их нет, и возвращает их коды. Как `init` старой программы |
| `POST /transactions` | Пакет до 100 операций: `{external_ref, device, received_at, occurred_on, kind EXPENSE/INCOME/REFUND/TRANSFER, account_code, to_account_code, amount, category_code, place_code, for, description, translations, needs_review}`. Для каждой — `MATCHED` (с описанием ручной операции), `CREATED`, `DUPLICATE` или `REJECTED` (с ошибкой); `transaction_id`, `needs_review` |
| `GET /transactions?refs=…` | Состояние своих операций: есть ли, «не проверено» ли, удалена ли. Для 7.5 и отметки «удалена» |
| `PUT /transactions/{external_ref}` | Категория, место, «для кого», описание. Только для операций, заведённых из SMS, с отметкой «не проверено», иначе `409` |
| `POST /pending` | Пакет отметок: `{external_ref, device, sender, received_at, reason, amount?, currency?, account_code?, account_number?, text?}`. `text` — только после «Отправить Claude». Для `BALANCE_GAP` — сумма разрыва и счёт |
| `DELETE /pending/{external_ref}` | Отметка закрыта на Mac |
| `GET /pending?resolved_since=` | Какие отметки закрыли на сайте или через Claude (7.6) |
| `GET /config`, `PUT /config` | Копия настроек: JSON ≤ 256 КБ, `ETag` — версия, `PUT` с `If-Match`, при конфликте `412` |
| `GET /hints?account&amount` | Подсказки по истории (6.5) |

С этим токеном нельзя читать список операций, менять ручные операции и что-либо удалять. Склейка (7.3) меняет у
ручной операции только `external_ref`.

### 10.2. Изменения в family-budget

1. **`transactions`.**
   - Колонки `external_ref TEXT NULL` с уникальным индексом `(project_id, external_ref) WHERE external_ref IS NOT
     NULL`; `source TEXT NULL` (`WEB`, `MCP`, `API`, `SMS`; старые строки — NULL); `needs_review BOOLEAN NOT NULL
     DEFAULT false` и частичный индекс `(project_id) WHERE needs_review`; `sms_received_at TIMESTAMPTZ NULL`.
   - Поля в `TransactionInput` (необязательные) и `TransactionDto`. `PUT` не меняет `external_ref`, но снимает
     `needs_review`.
   - Методы сервиса: `find_by_external_ref`; `match_candidates` и выбор ближайшего (7.3); `attach_external_ref`;
     `merge_into_sms` — дополнить операцию из SMS при ручном вводе и `split` для «Это другая покупка»;
     `history_hints`; `review_context` — ручные записи рядом по времени и операции с той же суммой на других
     счетах (10.4); `mark_reviewed`.
   - Список операций (10.3).
   - Поля общие: так же будут защищаться от дублей и помечать источник Telegram-бот, импорт выписок и слипы.
2. **Фича `autoimport`.** API 10.1, таблицы 11.2, порты к `transactions`, `categories`, `accounts`. Блок
   «Устройства импорта» в настройках проекта: имя Mac, когда последний раз присылал, версия приложения, число
   отметок, «Скачать копию настроек».
3. **`projects`.** Право токена в форме API-токена (`templates/projects/security.html`).
4. **`mcp`.** Инструменты и абзац инструкции сервера из 10.4.
5. **`wire_projects.rs`.** `purge_one!("autoimport", ::autoimport::Service)`: удаление проекта стирает отметки,
   копию настроек и устройства.
6. **Демо (`seed.rs`).** Операции из SMS (склеенные, заведённые, непроверенные) и отметки, включая разрыв цепочки.

### 10.4. Разбор вместе с Claude: инструменты MCP

Задача: если человек не внёс покупку, она всё равно есть в бухгалтерии и остаток верен. Потом Claude находит такие
операции и спрашивает, что это было, а человек отвечает своими словами.

У операции, заведённой из SMS без ручной пары: `source = SMS`, `needs_review = true`, время SMS
(`sms_received_at`), категория из заполнения («Нераспределённые»), описание из заполнения с контрагентом («KBank:
перевод на X-8842»).

| Инструмент | Что делает |
| --- | --- |
| `list_review` | Главный инструмент. Параметры: период (по умолчанию 7 дней), счёт. Возвращает по дням: **непроверенные операции** — id, время SMS, счёт, сумма, вид, описание, текущая категория, подсказки по истории (6.5), до трёх ручных записей того же дня, ближайших по времени («в 12:40 записан обед в Major Pinklao»), ручные операции с той же суммой в тот же день **на другом счёте** без SMS («записано наличными, а списано с карты?»); **отметки «ждёт разбора»** — время, отправитель, причина, сумма, текст, если его отправили; **итоги** — сколько SMS склеилось с ручными записями, сколько заведено, сколько непроверенных старше периода |
| `update_transaction` | Уже есть. Любое изменение операции с отметкой «не проверено» снимает отметку: человек ответил. `reviewed: false` — оставить отметку |
| `mark_reviewed` | `{ids}` — «всё верно» или «не помню»: оставить как есть и больше не спрашивать |
| `record_pending` | Завести операцию по отметке «ждёт разбора» (сумма и счёт из отметки или со слов человека) и закрыть отметку |
| `dismiss_pending` | Пропустить отметку |
| `list_transactions` | Новые фильтры `source` и `needs_review` |
| `add_expense`, `add_income` | Дополняют операцию из SMS (7.3) и говорят об этом в ответе; `new: true` — отдельная операция. В ответе ещё `unreviewed_count` — сколько непроверенных в проекте |

Абзац в инструкции MCP-сервера (`INSTRUCTIONS` в `crates/features/mcp/src/adapters/server.rs`), чтобы так
работала любая сессия Claude, а не только задача по расписанию:

> Transactions with needs_review were created from bank SMS: amount, account and time are facts, the category is a
> placeholder. Ask the user what they were in one message, numbered, with hints from list_review; never pick a
> category without the user's answer. Apply each answer with update_transaction; "don't remember" or "all
> correct" → mark_reviewed. When a write result shows unreviewed_count > 0, mention it once per conversation.

Настройки разбора на Mac Claude в v1 не меняет: сервер не разбирает документ настроек. Менять исключения через
Claude — этап 5: для этого сервер должен подключить крейт `core`.

### 10.5. Когда и как Claude спрашивает

**Когда:**

- **Вечером по расписанию.** Задача в claude.ai: каждый день в 20:40 по Бангкоку, новая сессия, коннектор
  family-budget, push-уведомление на телефон. Ничего нет — сессия завершается молча.
- **По просьбе**: «что не разобрано?», «разберём автоматические».
- **Попутно.** Человек вносит трату через Claude, в ответе `unreviewed_count > 0` — Claude одной строкой в конце
  упоминает: «кстати, с утра 2 неразобранных списания, разберём?». Не чаще раза за разговор.
- **Чек позже.** Фото чека, присланное вечером, само дополняет операцию из SMS (7.3): отдельного вопроса не нужно.

**Как:**

1. Одно сообщение на всё. По порядку времени, с номерами. Похожие подряд объединяются: «3 × 60 ฿ утром — кофе,
   как обычно?».
2. В каждой строке: время, сумма, счёт и зацепка — подсказка по истории, ручная запись рядом по времени или
   операция на другом счёте с той же суммой.
3. Человек отвечает как удобно и не обязательно про всё: «1 кофе, 3 такси, 2 не помню». Неотвеченное
   остаётся до следующего раза.
4. «Не помню» → `mark_reviewed`: остаётся в «Нераспределённых», больше не спрашивается.
5. Непроверенные старше недели не вываливаются списком. Claude называет их число и предлагает закрыть как «не
   помню».
6. Отметки «ждёт разбора» — после операций. Разрыв цепочки: «по K-Bank прошло 120 ฿ без SMS между 10:31 и
   10:54 — что это?». Нераспознанное SMS без текста: «открой “Входящие” в приложении на Mac». `HAS_LINK` —
   «похоже на мошенничество, ничего не завожу».
7. В конце — одна строка итога: «Готово: 3 разобрано, 1 оставил в Нераспределённых».

Пример:

```
Claude: За 21.10 по K-Bank 7 списаний, 5 нашли твои записи. Не внесено:
        1. 10:59 · 60 ฿ — раньше 60 ฿ было «Кофе и чай · Café Amazon». Так же?
        2. 19:02 · 813 ฿ — что это? В 18:50 ты записал такси до Big C.
        И по K-Bank прошло 120 ฿ без SMS между 10:31 и 10:54 — что это было?
Человек: 1 да, 2 big c продукты, 120 не помню
Claude: Готово: кофе и «Продукты · Big C» записал, 120 ฿ оставил в Нераспределённых.
```

Claude ничего не меняет молча: каждое изменение — по ответу человека. Задачу по расписанию Claude заводит сам,
когда готовы инструменты 10.4 (этап 3). Когда сервер научится промптам MCP (`docs/mcp-plan.md`, этап 5), сюда
добавится промпт «Разобрать автоматические».

### 12.5. Надёжность и секреты

1. Токен — в Keychain: сервис `family-messages-sync`, аккаунт — URL бухгалтерии. В файлах токена нет.
2. Операции уходят пакетами до 100, по порядку `ROWID`. Ошибка сети или `5xx` → `QUEUED`, повтор на следующем
   проходе (раз в 30 секунд, после трёх неудач подряд — раз в 5 минут). Сервер принимает повторы (7.2).
3. `401` / `403` → в «Сводке» и логе: «токен отозван или нет права autoimport:write — выполните set-token».
4. Один экземпляр каждого процесса: блокировка `.lock`. Занято — молча выйти, как в старой программе.
5. Тексты сообщений, остатки и токен в лог не пишутся. Лог прохода — итоги: `склеено 6, заведено 1, во входящих 1,
   отсеяно 3`.
6. URL `http://` разрешён только для `localhost` и `127.0.0.1`.

### 12.6. Тесты и CI

- `core`: «Пропускать», форматы и метки, суммы, валюты, номера карт, заполнение и его порядок, `process` на всех
  причинах, цепочка остатков (разрыв, SMS не по порядку), готовые форматы на реальных SMS KBank с изменёнными
  суммами и на примерах из тестов старой программы (номер карты не влияет, OTP отсеивается), `attributedBody`,
  даты Apple.
- `reader`: `chat.db` создаётся в тесте через rusqlite; копируются только отправители из списка; текст не
  расшифровывается; первый запуск; `backfill_since`; очистка по сроку; статистика без текстов.
- `app`: поддельная очередь и поддельный сервер (`httpmock`): `MATCHED`, `CREATED`, `DUPLICATE`, сервер выключен
  → `QUEUED` → отправлено без потерь, отметки без текста, текст только после «Отправить Claude», конфликт копии
  настроек `412`, отправители с сервера не применяются без подтверждения. Интерфейс: чужой `Host` → `403`,
  `POST` без CSRF → `403`, текст SMS экранируется.
- CI в GitHub Actions: ubuntu — `cargo fmt --check`, `clippy -D warnings`, `cargo test`; macos —
  `cargo build --release`; проверка, что у читателя нет сетевых зависимостей (`cargo tree -p reader` без
  `reqwest`, `hyper`, `tokio`).

### 12.7. Переход со старой программы

1. Создать в бухгалтерии токен «Автоимпорт SMS с Mac».
2. `make deploy`: `setup` предложит взять отправителей из старого конфига, поставит готовые форматы KBank,
   спросит счёт для номера карты.
3. `make legacy-uninstall`: старая программа больше не пишет в старый API.
4. `backfill --since` за прошлый месяц: SMS склеятся с ручными записями, а то, что забыли внести, окажется
   непроверенными операциями и разрывами цепочки.

## 13. Безопасность и приватность

| Угроза | Мера |
| --- | --- |
| Личная переписка | Читатель копирует только отправителей-банков. Список, пришедший с сервера, на этом Mac применяется только после подтверждения здесь |
| Тексты SMS на сервере | Не уходят. Только операции и отметки без текста. Текст одного сообщения уходит по кнопке «Отправить Claude» и стирается на сервере, когда отметку закрыли |
| Остатки счетов | Не уходят на сервер, не пишутся в лог. Сверка на Mac |
| Коды подтверждения | Выбрасываются приложением (`DROPPED`), не уходят никуда и не пишутся в лог. В очереди на Mac лежат до конца срока хранения, как и в самом `chat.db` |
| Процесс с доступом ко всему диску | Только читатель: без сети, без разбора, около 200 строк |
| Локальный интерфейс | Только `127.0.0.1`, проверка `Host`, вход по одноразовой ссылке, cookie `SameSite=Strict`, CSRF, автоэкранирование (8.4) |
| Файлы на Mac | Каталог `0700`, `spool.db` и `app.db` в Library пользователя, срок хранения 90 дней |
| Утечка токена с Mac | Токен в Keychain. Право `autoimport:write`: только заводить операции из SMS, прикреплять SMS к ручным, менять свои непроверенные, отметки и копию настроек. Нельзя читать список операций, менять ручные, удалять. Токен привязан к проекту, отзывается в профиле |
| Подменённая копия настроек на сервере | Может испортить разбор на Mac, но не расширить список отправителей без подтверждения. Конфликт версий не перезаписывается молча |
| Поддельные SMS от имени банка | Сообщение со ссылкой не заводится (`HAS_LINK`). Остальное без ручной пары заводится «не проверено». Поддельное SMS рвёт цепочку остатков |
| Инструкции в тексте SMS для Claude | Текст попадает к Claude только по кнопке. Тексты — данные. Claude меняет операции только по ответу человека. Удалять через MCP нельзя |
| Тяжёлые regex | Крейт `regex` работает за линейное время. Образец ≤ 1000 символов, `RegexBuilder::size_limit` |
| Перехват | HTTPS обязателен (кроме localhost) |
| Чужой проект, роли | Всё по `scope.project_id`. Тесты «чужой проект → 404» и «VIEWER → 403» для каждого эндпоинта |

## 15. Критерии приёмки

- [ ] Ручная операция «Капучино» 60 ฿ по K-Bank внесена в 10:55. SMS `Withdrawal 60.00` в 10:59 → `MATCHED`,
      новой операции нет, у ручной появилась отметка «SMS».
- [ ] Две ручные записи по 89 ฿ и два SMS по 89 ฿ за минуту → оба `MATCHED`, каждое со своей записью.
- [ ] SMS `Withdrawal 813.00` без ручной пары → расход 813 THB на «Нераспределённые расходы» датой получения, с
      отметкой «не проверено». Текста SMS и остатка на сервере нет.
- [ ] SMS пришло первым, через 10 минут чек на ту же сумму вносится через Claude → `add_expense` дополняет
      операцию из SMS позициями чека и снимает отметку, операция одна. С `new: true` — две операции.
- [ ] `Deposit 11,088.02` без пары → доход на категорию дохода по умолчанию.
- [ ] Исключение «контрагент `X-8842` → “Переводы близким”, для кого — получатель» превращает `transferred 500.00 Baht
      to A/C X-8842` без ручной пары в расход этой категории без отметки «не проверено».
- [ ] Исключение «контрагент `X-1234` → перевод на “Накопительный”» делает перевод между своими счетами, расходы
      бюджета не меняются.
- [ ] Цепочка остатков с пропуском 120 ฿ → отметка `BALANCE_GAP` на 120 ฿ по K-Bank, Claude о ней спрашивает.
- [ ] После всех склеек «Сводка» показывает одинаковый остаток банка и бухгалтерии. Ручная операция удалена →
      расхождение видно.
- [ ] Три проверенные операции по 60 ฿ в «Кофе и чай · Café Amazon» → у новой непроверенной на 60 ฿ подсказка
      «Кофе и чай · Café Amazon», сама категория не меняется.
- [ ] `list_review` возвращает непроверенные операции по дням с подсказками и ручными записями рядом по времени.
      Ответ «не помню» → `mark_reviewed`, операция остаётся в «Нераспределённых», в следующем `list_review` её
      нет.
- [ ] Ручная запись 89 ฿ наличными и SMS о списании 89 ฿ с карты в тот же день → `list_review` показывает их
      рядом как возможно одну покупку.
- [ ] `add_expense` при непроверенных операциях в проекте возвращает `unreviewed_count`.
- [ ] Неизвестный формат → во «Входящих» приложения с текстом, на сервере отметка без текста, Claude о ней
      сообщает. «Создать формат» → живая проверка ✓ → «Применить к подходящим» заводит операцию, отметка на
      сервере закрывается.
- [ ] «Отправить Claude» у одного сообщения отправляет его текст; после закрытия отметки текста на сервере нет.
- [ ] Сообщение с OTP → `DROPPED`, на сервер ничего не уходит. Строка «Пропускать» для рекламы, добавленная в
      интерфейсе, выбрасывает рекламу со следующего прохода.
- [ ] SMS от «KBank» со ссылкой → `HAS_LINK`, операции нет.
- [ ] Одно и то же SMS дважды (одинаковый текст, разные `guid`) → второе во «Входящих» с `DUPLICATE_TEXT`.
- [ ] Сообщения не от банков не попадают в `spool.db`: проверяется по файлу.
- [ ] Первый проход читателя ничего не копирует. `backfill --since` загружает историю, ручные операции
      склеиваются, забытые становятся непроверенными.
- [ ] Сервер выключен на час, пришло 5 SMS. После включения все 5 обработаны, ни одно не потеряно и не задвоено.
- [ ] Два Mac с одним Apple ID дают одну операцию (`DUPLICATE` у второго).
- [ ] Настройки, изменённые на Mac, через минуту есть на сервере. На втором Mac «Восстановить с сервера» даёт те
      же настройки; отправители применяются только после подтверждения.
- [ ] `make update` обновляет приложение, читатель продолжает работать без повторной выдачи Full Disk Access.
- [ ] Без Full Disk Access «Сводка» и `status` показывают причину и путь к читателю.
- [ ] Запрос к интерфейсу с `Host: evil.example` → `403`. `POST` без CSRF-токена → `403`.
- [ ] Токен `autoimport:write` получает `403` на `GET /api/transactions` и на изменение ручной операции. Чужой
      проект → 404.
- [ ] Удаление проекта удаляет отметки, копию настроек и устройства.
- [ ] Все тесты обоих репозиториев проходят без БД и без сети. У читателя нет сетевых зависимостей.

## 16. Вне рамок v1

- Push-уведомления приложения K PLUS: читатель их не видит, только SMS и iMessage. Операции, о которых пришёл
  только push, видны как разрывы цепочки остатков.
- Наличные и кошельки без SMS по-прежнему вносятся фразой или фото через Claude.
- Связка двух сторон перевода между своими счетами, когда SMS приходят от обоих банков. В v1 одна сторона
  превращается в перевод исключением, другая пропускается исключением с действием `SKIP`.
- Покупки в валюте, отличной от валюты счёта: такие сообщения остаются во «Входящих».
- Настройка с телефона: она живёт там, где сообщения.
- Прямое подключение к банкам. Тайские банки не подключаются к агрегаторам. Проект Банка Таиланда «Your Data»
  открывает обмен данными постепенно: с конца 2026 года данные депозитных счетов, остальное в 2027–2028.
- Другие источники. Крейт `core` от источника не зависит, поэтому позже подключаются, например:
  - слипы из галереи телефона в мобильном приложении. У тайских слипов есть QR-код для проверки перевода. Это
    может оказаться надёжнее распознавания картинки, но какие данные он даёт, нужно изучить отдельно;
  - автоматизация «Команд» на iPhone;
  - Android;
  - почта и Telegram — на сервере, с крейтом `core`.
- Несколько проектов из одного приложения: одна установка — один токен — один проект.
