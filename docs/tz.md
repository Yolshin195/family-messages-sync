# ТЗ: сообщения банка → семейная бухгалтерия

16.10.2026 · версия 1

Банковские SMS приходят на Mac и становятся транзакциями в
[family-budget](https://github.com/Yolshin195/family-budget). Что заводить, в какой счёт и категорию, решают
шаблоны и правила. Их настраивают в интерфейсе бухгалтерии.

Работа делится на две части в двух репозиториях:

| Часть | Репозиторий | Что это |
| --- | --- | --- |
| **A. Программа `family-messages-sync`** | этот | Фоновая программа на Mac. Читает SMS из Messages, отбрасывает коды подтверждения, отправляет сообщения банка в бухгалтерию |
| **B. Фича `inbox` «Сообщения банка»** | family-budget | Хранит сообщения, шаблоны, правила и привязки карт к счетам. Разбирает сообщения, заводит транзакции. Даёт экраны настройки и проверки |

Связь между частями — HTTP API из раздела 8. A и B можно делать параллельно.

Предыдущая версия — `accounting-messages-sync`: одна программа, правила-regex в `config.json`, старый Accounting API.
Из неё переносится в A: чтение `chat.db`, в том числе текста из `attributedBody`; курсор по `ROWID`; Keychain;
launchd; `make deploy`; инструкции по Full Disk Access.

## 1. Решение: правила хранятся в бухгалтерии

Шаблоны и правила хранит и применяет бухгалтерия. Программа на Mac только отправляет сообщения и в разборе не
участвует.

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| JSON-конфиг на Mac (как сейчас) | Просто, бухгалтерию менять не нужно | Regex правят в файле. Шаблон не проверить на реальных сообщениях. Коды счетов и категорий не проверяются: опечатка всплывёт только ошибкой при отправке. Нераспознанное попадает в лог-файл |
| SQLite на Mac + свой интерфейс | SMS не покидают Mac | Второй интерфейс с нуля. Списки счетов и категорий пришлось бы тянуть через API. Править можно только с этого Mac, с телефона нельзя. Повторный разбор уже полученных сообщений пришлось бы писать отдельно |
| **Правила и разбор в бухгалтерии, на Mac только отправка (выбрано)** | Один интерфейс с дизайн-системой, ролями, тремя языками и телефоном. Счета и категории выбираются из списков и проверяются. Нераспознанное лежит во «Входящих»: из него делается шаблон, шаблон проверяется на реальных сообщениях и применяется к уже полученным. Программа на Mac почти не меняется, поэтому Full Disk Access не приходится выдавать заново после каждой правки правил. Дубли отсекает сервер. Второй Mac, Telegram и почта смогут использовать те же правила | Нужна новая фича в family-budget. Тексты банковских SMS хранятся на сервере (без кодов подтверждения, с ограниченным сроком хранения, раздел 12) |

Промежуточный вариант «правила в бухгалтерии, разбор на Mac» отклонён. Чтобы проверять шаблон на реальных
сообщениях и показывать нераспознанное, сообщения всё равно должны лежать на сервере. Разбор пришлось бы делать
дважды.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Сообщение | Входящее SMS или iMessage от банка: отправитель, текст, время получения, источник |
| Источник | Устройство, с которого пришло сообщение («MacBook Алексея»). Только для информации |
| Шаблон | Как разобрать текст одного формата: фильтр отправителя, образец с метками (`{amount}`, `{account}`…) или regex, тип операции |
| Правило | Что делать с разобранной операцией: условия (продавец, счёт, сумма, текст) → действие (завести в категорию, перевод, на проверку, пропустить) |
| Маска счёта | Последние 4 цифры карты или счёта из текста (`X-5019` → `5019`), привязанные к счёту бухгалтерии |
| На проверке | Разобранное сообщение ждёт решения человека: «Завести» или «Пропустить» |

## 3. Путь сообщения

```
Mac (часть A)
  chat.db → отправитель из списка банков? → не код подтверждения? → пакет до 50 сообщений
          → POST /api/inbox_ingest/messages  (Bearer-токен, право inbox_ingest:write)
Бухгалтерия (часть B)
  external_id уже есть? → ответ «дубль», ничего не делаем
  сохранить → первый подходящий шаблон → извлечь поля → найти счёт → первое подходящее правило
            → действие: завести транзакцию / на проверку / пропустить
```

Сообщение обрабатывается сразу при приёме. Статусы возвращаются в ответе, и программа на Mac пишет их в лог.

| Статус | Значение | Требует внимания |
| --- | --- | --- |
| `CREATED` | Транзакция заведена автоматически | нет |
| `CONFIRMED` | Транзакция заведена вручную из «На проверке», «Не распознано» или «Ошибка» | нет |
| `REVIEW` | Разобрано, ждёт решения. Причина в `reason` (раздел 6) | **да** |
| `UNRECOGNIZED` | Ни один шаблон не подошёл | **да** |
| `ERROR` | Разобрано, но транзакция не создалась. Текст ошибки в `error` (например, счёт в архиве) | **да** |
| `IGNORED` | Пропущено шаблоном или правилом | нет |
| `DISMISSED` | Пропущено вручную | нет |

## 4. Шаблоны

Шаблон описывает один формат сообщения, например «KBank: списание». Шаблоны проверяются по порядку, побеждает
первый подходящий. Отключённые пропускаются.

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| Название | да | «KBank: списание» |
| Отправитель | нет | Подстрока в отправителе без учёта регистра (`kbank`). Пусто — любой |
| Синтаксис | да | `TEMPLATE` — образец с метками (по умолчанию); `REGEX` — регулярное выражение для сложных случаев |
| Образец | да | Текст образца или regex, до 1000 символов |
| Тип операции | да | `EXPENSE` расход, `INCOME` доход, `REFUND` возврат (расход с обратными знаками), `TRANSFER` перевод, `IGNORE` пропустить |
| Счёт по умолчанию | нет | Используется, если `{account}` нет в тексте или маска не привязана |
| Счёт зачисления | для `TRANSFER` | Куда перевод, например снятие наличных: карта → «Наличные» |
| Порядок дат | нет | `DMY` (по умолчанию), `MDY`, `YMD` — как читать `{date}` |
| Порядок, включён | да | Позиция в списке, переключатель |

### 4.1. Образец с метками

Образец — это текст сообщения, где изменяемые части заменены метками. Правила сопоставления:

- регистр не важен;
- любая последовательность пробелов совпадает с любой другой;
- остальной текст сравнивается буквально, спецсимволы экранируются;
- образец ищется внутри сообщения, а не сравнивается с ним целиком;
- каждая метка, кроме `{*}`, встречается не больше одного раза;
- для типов кроме `IGNORE` метка `{amount}` обязательна.

| Метка | Что совпадает | Пример |
| --- | --- | --- |
| `{amount}` | Сумма операции: цифры, разделители тысяч (`,` пробел NBSP `'`), дробная часть через `.` или `,` | `11,088.02`, `1 234,56` |
| `{balance}` | Остаток после операции, формат как у суммы | `8,195.25` |
| `{currency}` | Валюта: код или символ. Сопоставляется по таблице 4.4 | `Baht`, `฿`, `THB`, `₽`, `руб.` |
| `{account}` | Номер карты или счёта (непробельные символы, в конце не меньше 4 цифр) | `X-5019`, `*1234`, `MIR-1234` |
| `{merchant}` | Продавец или контрагент: минимально возможный текст до следующей части образца, в конце образца — до конца строки | `7-ELEVEN SUKHUMVIT` |
| `{date}` | Дата: `d/m/yy`, `d.m.yyyy`, `yyyy-mm-dd`; разделители `/ . -` | `21/09/26` |
| `{time}` | Время `h:mm` или `h:mm:ss` | `10:50` |
| `{*}` | Любой текст, минимально возможный. Можно использовать несколько раз | |

Образец компилируется в regex крейта `regex`. В форме видно, во что он скомпилировался: так удобнее перейти на
синтаксис `REGEX`.

Синтаксис `REGEX` — это regex крейта Rust (без lookahead и lookbehind). Именованные группы называются так же, как
метки: `amount`, `balance`, `currency`, `account`, `merchant`, `date`, `time`. Группа `amount` обязательна для
типов кроме `IGNORE`.

### 4.2. Примеры: KBank

| Сообщение | Образец | Тип |
| --- | --- | --- |
| `21/09/26 10:50 A/C X-5019 Withdrawal 60.00 Outstanding Balance 8,195.25 Baht.` | `{date} {time} A/C {account} Withdrawal {amount} Outstanding Balance {balance} {currency}.` | `EXPENSE` |
| `20/09/26 11:44 A/C X-5019 Deposit 11,088.02 Outstanding Balance 12,282.25 Baht.` | `{date} {time} A/C {account} Deposit {amount} Outstanding Balance {balance} {currency}.` | `INCOME` |
| `20/09/26 21:26 A/C X-5019 transferred 120.00 Baht to A/C X-8842 Outstanding Balance 10,002.25 Baht.` | `{date} {time} A/C {account} transferred {amount} {currency} to A/C {merchant} Outstanding Balance {balance}` | `EXPENSE` (правило может сделать из него перевод, раздел 5) |
| `OTP 123456 (Ref. ABCD) for K PLUS` | `OTP` | `IGNORE` (на сервер не попадает, раздел 11.4; шаблон на случай другого отправителя) |

### 4.3. Готовые шаблоны

В коде фичи лежит библиотека готовых шаблонов (`presets.rs`). На экране шаблонов есть кнопка «Добавить готовые»:
выбрать банк, и его шаблоны добавляются в конец списка. В v1 есть набор KBank: три шаблона из 4.2 плюс `IGNORE`
для OTP. Каждый готовый шаблон покрыт тестом на реальных примерах из таблицы 4.2. Новые банки добавляются
pull request'ом.

### 4.4. Разбор значений

**Сумма** (`{amount}`, `{balance}`) → `Decimal`:

1. Убрать пробелы, NBSP, узкие пробелы и апострофы.
2. Если есть и `,`, и `.`, дробный разделитель — тот, что правее. Второй удаляется.
3. Если разделитель один и встречается один раз, а после него 1–2 цифры, это дробная часть. Иначе это разделитель
   тысяч.
4. Если результат 0 или не число, сообщение получает статус `ERROR` («не удалось разобрать сумму»).

| Текст | Значение |
| --- | --- |
| `8,195.25` | 8195.25 |
| `1 234,56` | 1234.56 |
| `60.00` | 60 |
| `1,000` | 1000 |
| `1.234.567` | 1234567 |
| `1.5` | 1.5 |

**Валюта** (`{currency}`) сопоставляется с кодом в таком порядке:

1. Код или символ валюты из справочника проекта (порт к фиче `currencies`).
2. Встроенные синонимы: `Baht`, `บาท`, `฿` → THB; `руб`, `руб.`, `р.`, `₽` → RUB; `$` → USD; `€` → EUR.

Валюта не распозналась или не совпадает с валютой счёта → `REVIEW`, причина `CURRENCY_MISMATCH`. Покупки в другой
валюте бухгалтерия пока не поддерживает (ТЗ бухгалтерии, этап 8).

**Счёт** (`{account}`): из текста берутся цифры, последние 4 из них образуют маску (`X-5019` → `5019`). Маска ищется
в таблице «Маски счетов». Если маски нет, берётся счёт по умолчанию из шаблона. Если нет и его → `REVIEW`, причина
`ACCOUNT_UNKNOWN`. На экране сообщения есть «Привязать 5019 к счёту…», после этого сообщение обрабатывается
повторно.

**Дата операции:**

1. Есть `{date}`, она разобралась по порядку дат шаблона и отличается от даты получения не больше чем на 3 дня →
   берётся она. Двузначный год — это 20yy.
2. Иначе берётся дата получения по часовому поясу Mac (`received_at` приходит со смещением).

Ограничение в 3 дня отсекает мусор и годы буддийской эры.

## 5. Правила

Шаблон отвечает на вопрос «что это за операция и на сколько». Правило решает, куда её отнести и заводить ли.
Правила проверяются по порядку, побеждает первое подходящее. Отключённые пропускаются. Правила применяются только к
типам `EXPENSE`, `INCOME`, `REFUND` и `TRANSFER`.

**Условия.** Все заданные условия должны выполниться. Нужно хотя бы одно.

| Условие | Как проверяется |
| --- | --- |
| Тип операции | Равен (`EXPENSE` / `INCOME` / `REFUND` / `TRANSFER`) |
| Шаблон | Сообщение разобрано этим шаблоном |
| Счёт | Счёт, найденный по маске или взятый из шаблона, равен заданному |
| Продавец | `{merchant}` содержит текст или совпадает с regex (режим `CONTAINS` / `REGEX`, без учёта регистра) |
| Текст | Весь текст сообщения содержит подстроку или совпадает с regex (тот же режим) |
| Сумма | от / до, включительно |

**Действия:**

| Действие | Результат |
| --- | --- |
| `CREATE` | Завести как разобрано. Категория из правила; если не задана — категория по умолчанию из настроек |
| `TRANSFER` | Завести как перевод на счёт из правила (например, `transferred … to A/C X-8842` → «Накопительный») |
| `REVIEW` | На проверку. Форма заполнена из правила, причина `RULE_REVIEW` |
| `IGNORE` | Пропустить (`IGNORED`) |

У правила ещё есть описание транзакции. Это необязательный текст с подстановками `{merchant}`, `{account}`,
`{pattern}`. Если описание пустое, берётся `{merchant}`, а без него — название шаблона.

**Без подходящего правила** действие и категории берутся из настроек фичи (раздел 7, экран «Общие»):

- категория расхода и возврата по умолчанию (предлагается «Нераспределённые расходы»);
- категория дохода по умолчанию;
- режим «Заводить автоматически»: включён → `CREATE`, выключен → всё уходит в `REVIEW`, причина `AUTO_DISABLED`.
  Выключенный режим удобен первую неделю, пока шаблоны и правила ещё настраиваются.

Изменение шаблонов и правил не трогает уже заведённые транзакции. На них действует только повторная обработка
(6.3), и только на сообщения, требующие внимания.

## 6. Обработка

### 6.1. Алгоритм

Разбор — чистая функция домена без БД: `process(message, patterns, rules, masks, settings, refs) → Outcome`.
Её можно покрыть тестами без инфраструктуры.

1. Найти первый включённый шаблон, у которого подходит отправитель и совпадает образец. Не нашёлся →
   `UNRECOGNIZED`.
2. Тип шаблона `IGNORE` → `IGNORED`.
3. Извлечь поля (4.4). Не разобралась сумма → `ERROR`.
4. Определить счёт (4.4). Счёт не найден → `REVIEW` / `ACCOUNT_UNKNOWN`. Валюта не совпадает → `REVIEW` /
   `CURRENCY_MISMATCH`.
5. Найти первое подходящее правило. Нет правила → действие и категория из настроек.
6. Действие `IGNORE` → `IGNORED`. `REVIEW` или выключен режим «Заводить автоматически» → `REVIEW`. У перевода нет
   счёта зачисления → `REVIEW` / `TRANSFER_TARGET_MISSING`.
7. Проверить на возможный дубль (6.2). Похоже на дубль → `REVIEW` / `POSSIBLE_DUPLICATE`.
8. Создать транзакцию через порт к фиче `transactions`:
   - расход, доход, возврат: `{occurred_on, tx_kind, account_code, lines: [{category_code, amount}], refund,
     description, description_lang}`;
   - перевод: `{account_code, to_account_code, amount}`;
   - во всех случаях `external_ref = "inbox:<id сообщения>"`.

   Получилось → `CREATED` и `transaction_id`. Отказ валидации (счёт или категория в архиве, лишние знаки после
   запятой) → `ERROR` с текстом ошибки.

Разобранные поля, найденный шаблон, правило и итог сохраняются в сообщении. Так любое решение можно объяснить:
«шаблон “KBank: списание”, правило “7-Eleven → Продукты”».

### 6.2. Дубли

- **Точные.** Ключ — `(project_id, external_id)`. Повторная отправка того же сообщения ничего не создаёт: в ответе
  `duplicate: true` и текущий статус. При iCloud-синхронизации у сообщения одинаковый `guid` на всех Mac, поэтому
  два Mac с одним Apple ID не создадут дубль.
- **Возможные.** Это то же сообщение, пришедшее разными путями (например, уведомление о счёте на два телефона).
  Признак — тот же нормализованный текст (без учёта регистра и повторяющихся пробелов) от того же отправителя в
  пределах N минут (по умолчанию 10). Такие сообщения уходят в `REVIEW`, а не удаляются: две одинаковые покупки
  подряд бывают на самом деле.
- **Транзакция.** `external_ref` уникален в проекте (раздел 10). Если сбой случился между созданием транзакции и
  обновлением сообщения, повторная обработка получает конфликт, привязывает существующую транзакцию и не создаёт
  вторую.

### 6.3. Повторная обработка

- «Обработать заново» у одного сообщения в статусе `REVIEW`, `UNRECOGNIZED` или `ERROR`.
- «Применить к подходящим» после сохранения шаблона или правила. Обрабатываются сообщения, требующие внимания, за
  последние 90 дней. Сначала показывается предпросмотр («будет заведено 12, на проверку 3, пропущено 1»), потом
  подтверждение.
- Сообщения в `CREATED`, `CONFIRMED`, `IGNORED` и `DISMISSED` повторно не обрабатываются.

## 7. Интерфейс в бухгалтерии (часть B)

Приблизительные схемы всех новых экранов и шагов установки на Mac:

Пункт меню «Сообщения банка» (en: Bank messages, th: ข้อความจากธนาคาร), иконка Lucide `inbox`, основная группа.

Все экраны соблюдают правила ТЗ бухгалтерии:

- три языка;
- VIEWER только смотрит;
- шаблоны и правила меняют OWNER и EDITOR, как справочники.

| Экран | URL | Что делает |
| --- | --- | --- |
| Сообщения | `/inbox` | Список сообщений. Вкладки: «Требуют внимания» (по умолчанию: `REVIEW` + `UNRECOGNIZED` + `ERROR`, число в заголовке), «Заведены», «Пропущены», «Все». Фильтры: источник, отправитель, период, поиск по тексту. В строке: дата, отправитель, текст с подсветкой найденных частей, статус и причина понятными словами, итог («Расход 60 ฿ · KBank · Нераспределённые»), ссылка на транзакцию; если её удалили — «удалена». Действия: «Завести», «Пропустить», «Обработать заново», «Создать шаблон», «Создать правило» |
| Завести из сообщения | раскрывается в строке (htmx) | Форма заполнена из разбора: тип, счёт, категория (6 частых плюс поиск по дереву, как в быстром расходе), сумма, дата, описание. Флажок «Запомнить: “{merchant}” → категория» создаёт правило. Enter — «Завести» → `CONFIRMED` |
| Шаблоны | `/inbox/patterns` | Список по порядку: кнопки ↑ ↓, переключатель, сколько сообщений совпало за 30 дней. «Добавить», «Добавить готовые» |
| Форма шаблона | `/inbox/patterns/new?from=<id>`, `/inbox/patterns/{id}` | Поля из раздела 4 и скомпилированный regex. **Живая проверка** (htmx при вводе): последние 50 сообщений этого отправителя, у каждого ✓/✗ и таблица извлечённых полей; ошибки образца — под полем. «Сохранить» → предложение «Применить к N подходящим» (6.3) |
| Правила | `/inbox/rules` | То же: порядок, переключатель, число совпадений |
| Форма правила | `/inbox/rules/new?from=<id>`, `/inbox/rules/{id}` | Условия и действие из раздела 5. Живая проверка на последних 200 разобранных сообщениях: какие подходят и какие перехвачены правилом выше («перехвачено: “7-Eleven → Продукты”») |
| Настройки | `/inbox/settings` | Три блока. «Карты и счета»: маска → счёт; ниже маски, которые встречались в сообщениях, но не привязаны, с кнопкой «Привязать». «Если ни одно правило не подошло»: категории по умолчанию (расход и возврат, доход); «Заводить автоматически»; язык описаний (RU / EN / TH, по умолчанию язык владельца); окно дублей в минутах; срок хранения сообщений в днях (по умолчанию 365). «Источники»: имя Mac, когда последний раз присылал, сколько сообщений; кнопка «Создать токен для Mac» ведёт в «Профиль → Безопасность» |
| Готовые шаблоны | диалог на экране шаблонов | Выбрать банк → отметить его шаблоны → «Добавить» (в конец списка, без повторов) |
| Применить к подходящим | диалог после сохранения шаблона или правила | Предпросмотр по 6.3: что будет заведено, что останется на проверке. Кнопка «Завести N» |

«Создать шаблон из сообщения» заполняет образец текстом сообщения и заменяет в нём части на метки:

- даты → `{date}`, время → `{time}`;
- токены вида `X-5019`, `*1234` → `{account}`;
- число после слов balance / остаток / баланс / ยอดคงเหลือ → `{balance}`;
- первое из оставшихся чисел с дробной частью → `{amount}`;
- остальные числа → `{*}`.

Человек правит образец и сразу видит результат живой проверки.

Шаблоны, правила, маски и настройки удаляются по правилам раздела 9 ТЗ бухгалтерии: без «Вы уверены?», с тостом
«Отменить».

## 8. API

Пути, тела и ответы описаны в Swagger (utoipa), как у остальных фич. Ошибки в общем формате ядра.

### 8.1. Приём сообщений (для программы на Mac)

Пути вынесены под `/api/inbox_ingest/…`, поэтому токену Mac хватает права `inbox_ingest:write`. Ядро выводит
фичу права из пути (`kernel::auth::api_feature`). С таким токеном нельзя читать и менять транзакции, шаблоны и
правила (раздел 12).

`POST /api/inbox_ingest/messages`:

```json
{
  "source": "MacBook Алексея",
  "messages": [
    {
      "external_id": "imessage:9F2C1E7A-…",
      "sender": "KBank",
      "text": "21/09/26 10:50 A/C X-5019 Withdrawal 60.00 Outstanding Balance 8,195.25 Baht.",
      "received_at": "2026-09-21T10:50:12+07:00"
    }
  ]
}
```

Ответ `200`:

```json
{
  "results": [
    {
      "external_id": "imessage:9F2C1E7A-…",
      "id": "…uuid…",
      "duplicate": false,
      "status": "CREATED",
      "reason": null,
      "transaction_id": "…uuid…",
      "summary": "Расход 60.00 THB · KBANK_CARD · UNSORTED_EXPENSE"
    }
  ],
  "attention": 2
}
```

- В пакете не больше 100 сообщений, тело не больше 64 КБ (лимит ядра).
- Ограничения на сообщение: `external_id` до 200 символов, `sender` до 200, `text` от 1 до 4000, `received_at` в
  RFC 3339 со смещением.
- Сообщение, нарушившее ограничения, получает в ответе `status: "REJECTED"` и `error` и не сохраняется. Остальные
  сообщения пакета обрабатываются. Так одно испорченное сообщение не останавливает очередь.
- `422` на весь пакет — только при неверной структуре JSON или больше чем 100 сообщениях.
- `attention` — сколько сообщений проекта требуют внимания.

`GET /api/inbox_ingest/status` возвращает проект (id, название), пользователя токена, `attention` и время
последнего сообщения от каждого источника. Используется в `setup` и `status` программы.

`POST /api/inbox_ingest/preview` принимает `{sender, text, received_at}` и возвращает итог разбора без сохранения
и без создания транзакции: шаблон, правило, поля, счёт, категорию, дату, статус и причину. Используется в
`show --server`.

### 8.2. Управление (интерфейс и прочие клиенты)

Права: `inbox:read` / `inbox:write`, или сессия. Пути `/api/inbox/…`:

| Метод и путь | Действие |
| --- | --- |
| `GET /messages?status&source&sender&from&to&q` | Список, постранично (≤ 200) |
| `GET /messages/{id}` | Сообщение с разбором |
| `POST /messages/{id}/confirm` | Завести с полями из формы; необязательно `remember` (создать правило) → `CONFIRMED` |
| `POST /messages/{id}/dismiss` | → `DISMISSED` |
| `POST /messages/{id}/reprocess` | Обработать заново (6.3) |
| `POST /reprocess` | `{statuses, from, dry_run}` → итоги по статусам; `dry_run` по умолчанию `true` |
| `GET/POST /patterns`, `GET/PUT/DELETE /patterns/{id}`, `POST /patterns/{id}/move` | Шаблоны, порядок |
| `POST /patterns/test` | Образец → совпадения на последних сообщениях (живая проверка) |
| `GET /presets`, `POST /presets/{bank}/install` | Готовые шаблоны |
| `GET/POST /rules`, `GET/PUT/DELETE /rules/{id}`, `POST /rules/{id}/move`, `POST /rules/test` | Правила |
| `GET/PUT /account-masks`, `DELETE /account-masks/{mask}` | Маски счетов |
| `GET/PUT /settings` | Настройки |

## 10. Изменения в существующем коде family-budget

1. **`transactions`.** Новая колонка `external_ref TEXT NULL` и уникальный индекс `(project_id, external_ref)
   WHERE external_ref IS NOT NULL`. Поле `external_ref` в `TransactionInput` (необязательное) и в
   `TransactionDto`. Повтор даёт `409 Conflict` с id существующей транзакции. `PUT` поле не меняет. Сделано общим
   полем, чтобы так же защищались от дублей Telegram-бот и другие клиенты. Сервису — метод
   `find_by_external_ref`. Отметка «SMS» в списке операций со ссылкой на сообщение — желательно, этап 3.
2. **`projects`.** В форме API-токена (`templates/projects/security.html`) — вариант права
   `inbox_ingest:write` «Синхронизация SMS с Mac» с переводами на ru/en/th.
3. **`app/wiring/wire_inbox.rs`.** Порты фичи `inbox`:
   - `AccountsLookup` — активный ли счёт, его валюта, списки для форм;
   - `CategoriesLookup` — есть ли категория, её тип, дерево для выбора;
   - `CurrenciesLookup` — коды и символы для `{currency}`;
   - `Ledger` — `create` с `external_ref`, `find_by_external_ref`, `exists_many(ids)` для отметки «удалена»;
     `balance(account, date)` — на этапе 4.
4. **`wire_projects.rs`.** Строка `purge_one!("inbox", ::inbox::Service)`: удаление проекта стирает его сообщения
   и настройки.
5. **Workspace.** Зависимость `regex = "1"`. Иконка `inbox` в `scripts/build-assets.mjs`, затем `make assets`.
6. **Демо (`seed.rs`).** Готовые шаблоны KBank, маска `5019` → карта демо-семьи, 10–15 сообщений во всех статусах.

Фича делается по эталону rust-hex-api (вручную, как `transactions`):

- `domain.rs` — компиляция образцов, разбор значений, `process`, «образец из сообщения», готовые шаблоны;
- `ports.rs`, `service.rs`;
- `adapters/{http,web,postgres,memory}.rs`, `templates/inbox/*`;
- `migrations/`, `i18n.rs`, `tests.rs`, `FEATURE.md`.

## 11. Программа `family-messages-sync` (часть A, этот репозиторий)

Rust 2024, один бинарник, macOS 13+. Блокирующий ввод-вывод, без tokio.

### 11.1. Требования

Как у старой программы:

- Messages на Mac под тем же Apple ID, что на iPhone;
- на iPhone включено Text Message Forwarding;
- Full Disk Access выдан бинарнику в `~/.local/bin`;
- в бухгалтерии создан API-токен с правом `inbox_ingest:write` в нужном проекте, у пользователя роль OWNER или
  EDITOR.

### 11.2. Конфиг и состояние

`~/.config/family-messages-sync/config.toml`:

```toml
api_url = "https://budget.example.com"
device = "MacBook Алексея"                    # source в API
senders = ["kbank", "k plus", "kplus"]       # подстрока отправителя (handle.id), без учёта регистра
# Совпавшие сообщения не покидают Mac. По умолчанию — коды подтверждения на en/ru/th:
drop_patterns = [
  "(?i)\\botp\\b", "(?i)one[- ]time password", "(?i)verification code",
  "(?i)код подтверждения", "(?i)одноразов\\w* код", "(?i)никому не сообщайте",
  "รหัส\\s*OTP", "รหัสยืนยัน",
]
poll_interval_secs = 60
batch_size = 50
```

- `state.json`: `last_rowid`, `last_success_at`, `last_error`, `last_error_at`.
- Токен хранится в Keychain: сервис `family-messages-sync`, аккаунт — `api_url`. В файлах токена нет.
- Список отправителей — граница приватности. Он хранится только на Mac и сервером не меняется (раздел 12).

### 11.3. Команды

| Команда | Что делает |
| --- | --- |
| `setup` | Интерактивная настройка. Спрашивает URL, токен (ввод скрыт, сохраняется в Keychain) и имя устройства. Показывает отправителей из `senders` и даёт выбрать банки. Проверяет связь через `GET /api/inbox_ingest/status` и печатает проект и пользователя. Если есть конфиг старой программы (`~/.config/accounting-messages-sync`), предлагает взять из него `senders` и `ignore_patterns`. Текущие значения подставляются по умолчанию |
| `senders [--days 90]` | Отправители входящих за N дней: число сообщений и последний текст (OTP маскируется), чтобы найти банк |
| `show [N] [--server]` | Последние N сообщений банка и отбрасываются ли они локально. С `--server` — как их разберёт бухгалтерия (`preview`, без сохранения) |
| `sync [--dry-run]` | Один проход: отправить новые сообщения и выйти. С `--dry-run` только напечатать, что ушло бы |
| `daemon` | Постоянная работа для launchd: проход каждые `poll_interval_secs` |
| `backfill (--since YYYY-MM-DD \| --from-rowid N) [--dry-run]` | Отправить историю. Курсор не откатывается, дубли отсекает сервер |
| `status` | Диагностика: есть ли доступ к `chat.db` (FDA), есть ли токен в Keychain, ответ сервера и право токена, курсор, последняя удачная отправка, последняя ошибка, состояние агента launchd, `attention` |
| `set-token` | Заменить токен |
| `reset [-y]` | Удалить конфиг, состояние и токен, затем `setup` |

Если конфига нет и команда запущена в терминале, сначала запускается `setup`, как в старой программе. Без
терминала (под launchd) выводится понятная ошибка.

### 11.4. Чтение `chat.db`

- `~/Library/Messages/chat.db` открывается только на чтение.
- Запрос: `message.ROWID > last_rowid`, `is_from_me = 0`, `JOIN handle`, сортировка по `ROWID`, не больше 500
  строк за проход. Поля: `ROWID`, `guid`, `text`, `attributedBody`, `date`, `handle.id`.
- Текст берётся из `text`, а если там пусто — из `attributedBody` (typedstream). Перенести `text_from_attributed`
  из старой программы с тестами.
- `received_at` переводится из эпохи Apple (секунды или наносекунды с 2001-01-01) в RFC 3339 с локальным смещением.
- `external_id = "imessage:" + guid`.
- Сообщение отправляется, только если отправитель совпал с `senders`, текст не пуст и не совпал ни один
  `drop_patterns`. Остальные сообщения пропускаются молча, но курсор их проходит. Отброшенные локально считаются в
  логе; текст в лог не пишется.

### 11.5. Отправка и надёжность

1. Пакеты в порядке `ROWID`: не больше `batch_size` сообщений и не больше 48 КБ тела.
2. Курсор `last_rowid` сохраняется только после `200` за пакет. Если последние строки прохода не нужно
   отправлять, курсор тоже их проходит. Сервер принимает повторы, поэтому сбой после отправки и до сохранения
   курсора даёт повтор без дублей.
3. Сеть, `5xx` или `429` → курсор стоит, повтор с паузой 30 с → 1 мин → 2 мин → … → не больше 15 мин.
4. `401` или `403` → ошибка с подсказкой («токен отозван или нет права inbox_ingest:write — выполните
   set-token»), повтор раз в 15 мин.
5. `422` на весь пакет — ошибка программы. Курсор стоит, ошибка громко пишется в лог.
6. В ответе `REJECTED` → предупреждение в лог (rowid и причина), курсор идёт дальше.
7. Работает один экземпляр: блокировка файла `.lock`, как в старой программе.
8. На SIGTERM дождаться текущего запроса, сохранить состояние и выйти.
9. После сна или выключения следующий проход забирает всё накопленное.
10. Лог: одна строка на проход с итогами (`отправлено 3: CREATED 2, REVIEW 1; отброшено локально 1; внимание: 2`).
    Токен и тексты сообщений в лог не пишутся. Ошибка открытия `chat.db` выводится с подсказкой про Full Disk
    Access и путём к бинарнику.
11. URL `http://` разрешён только для `localhost` и `127.0.0.1`. Для остальных адресов нужен `https://`.
12. Уведомление macOS о новых сообщениях, требующих внимания, — по флагу `notify = true` (через `osascript`).
    Необязательно, этап 4.

### 11.6. Автозапуск

LaunchAgent `~/Library/LaunchAgents/local.family-messages-sync.plist`:

- `ProgramArguments`: `[bin, daemon]`;
- `RunAtLoad`, `KeepAlive`, `ThrottleInterval 30`;
- `ProcessType Background`;
- логи в `~/Library/Logs/family-messages-sync/{out,err}.log`.

Если нет Full Disk Access, программа не завершается, а пишет ошибку и повторяет попытку раз в 5 минут. Так
launchd не перезапускает её в цикле.

`Makefile` — как в старой программе: `deploy`, `build`, `test`, `install`, `setup`, `fda`, `plist`, `agent`,
`status`, `logs`, `run-now`, `stop`, `uninstall`. Плюс новый `legacy-uninstall`: выгрузить и удалить агента
`local.accounting-messages-sync` и его бинарник. Конфиг старой программы остаётся.

- правила курсора: сбой посередине, `REJECTED`, хвост без нужных сообщений.

Интеграционные тесты:

- `chat.db` создаётся в тесте через rusqlite: таблицы `message` и `handle` с нужными колонками;
- поддельный сервер на `TcpListener` или `httpmock`;
- сценарии: первый запуск, догонка после «сна», `5xx` → повтор без потерь, `401`, `backfill`, повторная отправка;
- Keychain подменяется через трейт.

CI в GitHub Actions:

- ubuntu: `cargo fmt --check`, `clippy -D warnings`, `cargo test`;
- macos: `cargo build --release`.

### 11.9. Переход со старой программы

1. Создать в бухгалтерии токен `inbox_ingest:write`, добавить готовые шаблоны KBank, привязать маску к карте,
   выбрать категории по умолчанию.
2. `make deploy`. `setup` предложит взять отправителей и фильтры из старого конфига.
3. `make legacy-uninstall`: старая программа больше не пишет в старый API.
4. Если нужна история: `family-messages-sync backfill --since 2026-10-01 --dry-run`, затем без `--dry-run`.

## 12. Безопасность и приватность

| Угроза | Мера |
| --- | --- |
| Личные переписки уходят на сервер | Отправляются только сообщения от отправителей из локального `senders`. Сервер этот список не меняет |
| Коды подтверждения | Отбрасываются на Mac (`drop_patterns`) и не попадают ни на сервер, ни в лог |
| Утечка токена с Mac | Токен в Keychain. Право только `inbox_ingest:write`: прочитать или изменить транзакции, шаблоны и правила нельзя, можно только прислать сообщение, которое пройдёт через правила. Токен привязан к одному проекту, отзывается в профиле, создание токена пишется в журнал безопасности |
| Перехват | HTTPS обязателен (кроме localhost). Сервер стоит за TLS 1.2+ (ТЗ бухгалтерии, раздел 13) |
| Тексты SMS на сервере | Хранятся `retention_days` (по умолчанию 365), стираются вместе с проектом, попадают в зашифрованные резервные копии |
| Тяжёлые regex | Крейт `regex` работает за линейное время. Ограничения: образец ≤ 1000 символов, `RegexBuilder::size_limit`. Ошибка компиляции показывается под полем |
| XSS через текст SMS | Автоэкранирование Askama, `safe` не используется |
| Чужой проект, роли | Всё по `scope.project_id`. Тесты «чужой проект → 404» и «VIEWER → 403» для каждого эндпоинта |

## 14. Критерии приёмки

- [ ] `21/09/26 10:50 A/C X-5019 Withdrawal 60.00 Outstanding Balance 8,195.25 Baht.` при маске `5019` → карта
      KBank и без правил → расход 60.00 THB на «Нераспределённые расходы» датой 21.09.2026, статус `CREATED`.
- [ ] `Deposit 11,088.02` → доход 11 088.02 на категорию дохода по умолчанию.
- [ ] Правило «текст содержит `X-8842` → перевод на “Накопительный”» превращает `transferred 120.00 Baht to A/C
      X-8842` в перевод «Карта → Накопительный», расходы бюджета не меняются.
- [ ] Сообщение с OTP не попадает на сервер: в `fb_inbox_messages` его нет, в логе программы «отброшено
      локально: 1».
- [ ] Повторная отправка того же пакета не создаёт ни сообщений, ни транзакций (`duplicate: true`). Два Mac с
      одним Apple ID дают одну транзакцию.
- [ ] Сервер выключен на час, за это время пришло 5 SMS. После включения все 5 заведены, ни одно не потеряно и не
      задвоено.
- [ ] Неизвестный формат → `UNRECOGNIZED` во вкладке «Требуют внимания» → «Создать шаблон» (метки подставлены),
      живая проверка показывает ✓ и поля → «Сохранить» → «Применить к подходящим» заводит транзакции.
- [ ] «Завести» с флажком «Запомнить» создаёт транзакцию и правило. Следующее сообщение того же продавца
      заводится в эту категорию автоматически.
- [ ] Изменение или удаление правила не меняет уже заведённые транзакции.
- [ ] Валюта операции не совпадает с валютой счёта → `REVIEW` / `CURRENCY_MISMATCH`, транзакции нет.
- [ ] Счёт в архиве → `ERROR` с понятным текстом. После возврата счёта «Обработать заново» заводит транзакцию.
- [ ] При выключенном «Заводить автоматически» всё разобранное попадает в `REVIEW`.
- [ ] Токен с правом `inbox_ingest:write` получает 403 на `/api/transactions` и `/api/inbox/rules`. VIEWER не
      может менять шаблоны и правила. Чужой проект → 404.
- [ ] Удаление проекта удаляет его сообщения, шаблоны, правила и настройки.
- [ ] `family-messages-sync status` без Full Disk Access показывает понятную причину и путь к бинарнику. Агент
      launchd не перезапускается в цикле.
- [ ] Все тесты обоих репозиториев проходят без БД и без сети. Разбор покрыт тестами на примерах из раздела 4
      (суммы, даты, маски, готовые шаблоны).

## 15. Вне рамок v1

- Push-уведомления приложения K PLUS: программа их не видит, только SMS и iMessage.
- Связка двух сторон перевода между своими счетами, когда SMS приходят от обоих банков. В v1 одна сторона
  превращается в перевод правилом `TRANSFER`, другая пропускается правилом `IGNORE`.
- Покупки в валюте, отличной от валюты счёта: такие сообщения уходят на проверку.
- Другие источники. API приёма от них не зависит, поэтому позже подключаются, например:
  - автоматизация «Команд» на iPhone («сообщение от KBank» → POST);
  - Android;
  - почта;
  - Telegram.
- Несколько проектов из одной программы на Mac: один конфиг — один токен — один проект.
